# 要求内容

## 概要

`docs/01` の Phase 0（技術検証と素材確認）を実施する。画面取得と入力が実機で成立するか、VRAM 4GBに収まるかを確かめ、結果を設計書へ反映する。

## 背景

`docs/02`〜`03` の設計は、未計測の前提に依存している。前提が外れると設計の手戻りが大きいため、Kahuna と大戦略SSB2 のどちらも本実装に入る前に、最もリスクの高い点を実機で確認する。

## 実装対象の機能

### 1. プロジェクトの土台
- Python 3.12 / uv の環境、`pyproject.toml`、lint・型検査・テストの実行環境を作る
- `docs/05` の検証コマンドが動く状態にする

### 2. Kahuna の画面取得と入力（Android）
- `adb` で SHG11 の画面を取得し、tap を送る
- Kahuna を起動して盤面・カード・杖コマ・カフナコマが読める画像が得られるか確認する

### 3. 大戦略SSB2 の画面取得と入力（PC）
- ゲームウィンドウを取得し、ウィンドウ相対座標でクリック・キー入力を送る
- 取得と入力が通らない場合の代替手段を検証する

### 4. VRAM の実測
- 大戦略SSB2 の実行中のGPUメモリ使用量を測る
- Qwen3-VL-2B / 4B（4bit）が同時に載るかを測り、載らない場合はCPU実行の速度を測る

### 5. 大戦略SSB2 の素材確認
- 兵器詳細画面と戦果予測画面が読める画像で得られるかを確認する
- 64×64 ヘックスのスクロールとカメラの挙動、ヘクスの見え方（形・角度）を確認する

### 6. 結果の反映
- 検証結果を `docs/` に反映し、「(仮)」の数値のうち計測できたものを置き換える

## 受け入れ条件

### プロジェクトの土台
- [ ] `uv sync` が成功する
- [ ] `ruff`、`mypy`、`pytest` が空のプロジェクトで通る

### Kahuna
- [ ] `adb -s <serial>` で画面を取得でき、画像が保存される
- [ ] tap を送り、画面が変化することを確認できる
- [ ] 盤面、手札、場札、決算の状態が目視で判別できる解像度であることを確認した
- [ ] 画面の種類（タイトル、ステージ選択、対戦中）を撮影し一覧にした（決算・カフナコマ・終了画面は Phase 1 のログで撮影する。2026-10-30 ユーザー承認）

### 大戦略SSB2
- [ ] ウィンドウの画像を取得でき、ウィンドウ相対座標が実際のクリック位置と一致する
- [ ] マウスクリックとキー入力（次部隊選択など）がゲームに届く
- [ ] 届かない場合は、管理者権限や別の入力方式での結果を記録した
- [ ] 兵器詳細画面と戦果予測画面を撮影し、数値が読める大きさか確認した

### VRAM
- [ ] 大戦略SSB2 の実行中のVRAM使用量を `nvidia-smi` で記録した
- [ ] VLM（2B）の同時実行の可否と、不可の場合のCPU実行の1回あたりの時間を記録した

### 結果の反映
- [ ] 検証結果を `docs/` の該当箇所へ反映し、設計と食い違う点を記録した
- [ ] 「(仮)」の数値のうち計測できたものを置き換えた

## 成功指標

- Phase 1 に進むための可否が、Kahuna と大戦略SSB2 のそれぞれについて判断できる
- 設計を変更すべき点が洗い出されている

## 前提・仮定

- 大戦略SSB2 の起動と画面の操作（マップの選択、対戦の開始）はユーザーが行う — 根拠: ゲームの起動やセーブ操作を自動化する要件がなく、検証の範囲外
- 検証用の画像は `datasets/` 等に保存し、Git管理しない — 根拠: `docs/04` の除外設定
- Kahuna の検証は SHG11（シリアル `355092380222016`）で行う — 根拠: 接続中の端末

## スコープ外

以下はこのフェーズでは実装しません:

- 盤面認識の実装（Phase 1 以降）
- ルールと思考ロジックの実装
- 実行ループ（`AgentRunner`）の本実装
- VLM の LoRA 学習
- Kahuna や大戦略SSB2 の自動プレイ
