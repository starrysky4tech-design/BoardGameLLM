# 設計書

> 事実の正本は `RESULT.md`(実機)と `docs/ideas/Maquis_アプリ内ルール.md`(アプリ内ルール)。本書は「何をどの部品に持たせるか」を決める。Phase 0 で確かめた事実は下の「Phase 0 で確定した事項」に反映済みで、確かめていないものは「未確認」と明記する。

## Phase 0 で確定した事項(設計への反映)

- **帰還は自動**。団員は行動後(または配置フェイズ後)、経路があれば自動で隠れ家へ戻り、無ければ捕縛される。したがって手に `Return` は要らない(下の手の表から削除)
- **手は3種**: `Place(location)`(配置。2タップ)、`Resolve(location, slot)`(行動ボタンの押下。地点をタップして右列の `slot` 枠を押す)、`EndPhase`(フェイズ・ターン終了)。協力者の勧誘・空中投下・射殺は、いずれも地点の行動ボタンに現れる `Resolve` の一種として扱う(手順は未確認のため、フェーズ3の実機で確かめて追加する)
- **配置は全員分を置かないと `EndPhase` できない**(画面上、右列の最下枠が空のまま)。行動フェイズは実行しない地点があってもよい
- **全団員の捕縛は即敗北**。配置の良し悪しは「置いた後に全団員の帰還経路が残るか」で決まる。画面の「!」(帰還不可)と地点の橙の数字(巡回が来る札の枚数)は、Strategy の見積もりの照合にも使える
- **山札と捨札は画面で一覧できる**(山札ボタン)。残りの数え上げは、毎回の読み取りで済む可能性が高い。ただし一覧の並びが引く順かは未確認なので、当面は「残りの多重集合」として扱い、順序は使わない
- 再開は HOME + `monkey` で状態が保たれる。`Recognizer` は「前の状態が無い」前提でも画面から状態を作れること(再開と評価セットの独立性のため)

## 未確認(フェーズ3 の実機の通しの記録で確かめて追記する)

勝ち・引き分けの画面、任務の★の進め方(特に暗殺)、山札の並びと切り直し、士気が下がる条件、空中投下・協力者の勧誘・射殺の手順。認識は、未知の画面で入力を送らず止まる。

## アーキテクチャ概要

Kahuna・Hive と同じ。`GamePlugin` の実装を `plugins/maquis/` に足し、共通基盤は触らない。`application` は `PluginRegistry` が設定のゲーム名から動的に読み込む。

```text
plugins/maquis/
├── __init__.py          # create_plugin()
├── logic/               # 画面に依存しない
│   ├── models.py        # Location, Resource, PatrolCard, Mission, MaquisState, MaquisMove
│   ├── board.py         # 場所と道(グラフ)、隠れ家までの到達判定
│   ├── rules.py         # 合法手、手の適用、逮捕、士気、任務、勝敗
│   ├── patrol.py        # 巡回カードの山札(残りの数え上げ、めくりの適用)
│   ├── strategy.py      # 山札の残りを無作為に並べるモンテカルロ
│   └── simulation.py    # 乱数で山札を引く自己プレイ(1ゲーム完走)
├── vision/
│   ├── screens.py       # 画面種別(起動、盤、行動の選択、任務、終局、禁止画面)
│   ├── tokens.py        # 場所ごとの駒(自分・民兵・兵士・空き)
│   ├── counters.py      # 資源、士気、日数、残りの人員の数字
│   ├── cards.py         # めくられた巡回カード、任務カードの判別
│   ├── recognizer.py    # 画面 → MaquisState
│   └── executor.py      # MaquisMove → タップ列
└── data/
    ├── board.json       # 場所、道、行動(出典つき)
    ├── patrol_cards.json# 巡回カード(出典つき)
    ├── missions.json    # 任務(出典つき)
    └── strategy.toml    # 試行回数、打ち切りの評価の重み
```

## 最初に決める設計上の論点

### 1. 相手は山札である(確率)
2人対戦の Kahuna・Hive は「相手の最善手」を仮定して探索した。Maquis の相手は巡回カードのめくりで、思考しない。そこで:

- 状態に**山札の残り(カードの多重集合)**を持つ。めくられたカードを認識で追い、捨て札から残りを数える
- 思考は「残りの山札を無作為に並べる → 既定の方針で数手番先(または終局)まで進める → 勝敗と評価値を平均する」を、候補の手ごとに繰り返す
- 山札の切り直しの時期(毎日か、尽きたときか)は**未確認**。規則は `patrol.py` の1か所に閉じ込める

### 2. `Rules.apply` の予測と実際の盤面の差
`AgentRunner` は `rules.apply(state, move)` の予測と、次に読んだ盤面を `rules.diff` で比べる(`application/runner.py`)。Maquis では、自分が人員を置いた直後にアプリが巡回カードをめくって民兵を置くので、予測には**分からない部分**(どこに民兵が来るか)が残る。

- `apply` は「自分の手で確実に決まる部分」だけを反映した盤面を返す
- `diff` は、確実な部分(自分の駒の位置、資源の増減)だけを比べ、巡回による変化は「めくられたカードと置かれた場所が、カードの定義と矛盾しないか」で検証する。矛盾すれば差異として返す(認識の誤りを疑って止まる)
- Kahuna の「山札から引いたカードは予測できない」と同じ扱いで、共通基盤の変更は不要と見ている。不足が出たら「インターフェースの不足」として記録する(`docs/01` のKPI)

### 3. 手の単位
1回の `execute` が1つの決定になるように切る。局面の段階(フェーズ)を状態に持ち、段階ごとに合法手の種類を変える。

| 段階 | 手(`MaquisMove`) | 備考 |
|---|---|---|
| 配置 | `Place(location)` | 人員を1人置く。その後アプリが巡回を置く(確率的) |
| 行動 | `Resolve(location, slot)` | 置いた人員の行動を1つ解決する。`slot` は右列の枠(0〜3)。解決した団員は経路があれば自動で帰還する |
| 共通 | `EndPhase` | 配置は全員を置いた後のみ可。行動は常に可(使わない地点があってよい) |

段階の区切りは確定(配置 → 行動 → 維持。維持は自動)。行動は順序を自由に選べる。協力者の勧誘・空中投下・射殺は `Resolve` の一種(手順は未確認)。

### 4. 盤は固定
場所と道は変わらない(建設で空き部屋の効果が変わるだけ)。Kahuna と同じく、盤の定義は `data/board.json` に置き、画面上の座標はキャリブレーション(`config/calibration/maquis-2432x1080.json`)に持つ。盤の拡大・移動があるかは**未確認**。

### 5. 認識の手段
- 駒(自分・民兵・兵士): 場所ごとの固定領域を色と形で分類する
- 数字(資源、士気、日数): テンプレートマッチング、だめなら OCR。VLM は使わない(`CLAUDE.md`: 密な数字は VLM が誤る)
- カード(巡回、任務): 絵柄または文字の固定位置のテンプレート照合。日本語の文字を読む必要があれば RapidOCR(Monopoly で導入済み)
- 山札の残りは画面に出ない可能性が高い。その場合は、手番ごとにめくられたカードを読んで自分で数える。**読み落としたら残りが分からなくなる**ので、読めなかったときは既定値で埋めずに止まる。再開時は「残り不明」として、切り直しまで全カード等確率で扱う

### 6. 禁止画面
「完全版を入手」(右上)、他ゲームの宣伝(右下)、ストアへ移る画面、統計のリセットの確認は禁止とし、`screens.py` で判別して入力を送らない。起動画面の該当領域へのタップは executor が拒否する。

## コンポーネント設計

### Rules (`logic/rules.py`、`board.py`、`patrol.py`)
**責務**: 段階ごとの合法手、手の適用、戻れない人員の逮捕、士気と兵士の増減、任務の達成、勝敗(`outcome` は "win" / "lose")。
**要点**: 場所・カード・任務の内容は JSON に置き、出典(アプリ内ルールの見出し)を書く。1ファイル300行を超えたら分割する(`docs/04`)。

### Strategy (`logic/strategy.py`)
**責務**: 合法手から1手を選ぶ。
**要点**: 候補の手ごとに、山札の残りを並べ替えた試行を持ち時間の中で繰り返す。試行の中の方針は軽い規則(任務に要る資源を優先、逮捕の危険がある配置を避ける)。打ち切りの評価は、任務の進み、人員の数、士気、残り日数の重み付き和(`data/strategy.toml`)。乱数は `random.Random` を引数で受ける。

### Recognizer (`vision/recognizer.py`)
**責務**: 画面 → `MaquisState` と `UiState`。直前の状態と比べて、めくられた巡回カードを山札の残りへ反映する。信頼度が足りなければ止まる。
**要点**: アニメーション(カードのめくり、駒の移動)の途中を読まない。`toolkit/waiting.poll` で画面が落ち着くのを待つ。

### MoveExecutor (`vision/executor.py`)
**責務**: `MaquisMove` をタップ列に変換し、実行後に画面の変化で結果を確認する。
**要点**: 確認のダイアログの有無、取り消し(Undo)の有無は Phase 0 で確かめる。

## データフロー

```text
1. 画面取得(adb) → Recognizer が MaquisState を作る(信頼度不足・禁止画面なら停止)
2. アニメーション中・アプリの処理中なら待つ
3. Rules.legal_moves → Strategy.choose(持ち時間)
4. MoveExecutor が操作 → 画面の変化で結果確認 → ログ保存
5. 次の認識で、予測(確実な部分)との差と、巡回カードの整合を確かめる
6. 終局の画面を検出したら停止(勝敗を記録)
```

## エラーハンドリング戦略

- 新しい例外クラスは作らない。`core/errors.py` の既存の例外と、`Recognition.low_confidence`、`ExecutionResult(success=False, reason=...)` で表す
- 想定外の画面、信頼度不足、禁止画面、合法手が0は、入力を送らず停止する。読み取りの失敗を既定値で埋めない
- めくられたカードが山札の残りに無い、置かれた場所がカードの定義と合わない場合は、認識かルールの誤りを疑って停止する
- 操作後に期待した変化が無ければ、再実行ではなく停止して画面を保存する

## テスト戦略

### ユニットテスト(`tests/plugins/maquis/unit/`)
- logic: 配置、巡回カードの置き先の優先順、逮捕(道の遮断)、各場所の行動、士気、任務、勝敗。**期待値はアプリ内ルールから手で作り、出典を書く**
- logic: 山札の数え上げ(めくった分が残りから減る、切り直し)
- logic: 固定シードの自己プレイで完走し、不正な手が出ない。戦略が無作為の方針より勝率が高い
- vision: 合成画像と、記録した実画面(`datasets/eval/maquis/`)。録画が無い環境は飛ばす
- vision: 禁止領域へのタップを executor が拒否する

### 統合テスト(`tests/plugins/maquis/integration/`)
- 記録画面でのドライラン、リプレイ

### 実機テスト(`tests/plugins/maquis/device/`)
- 画面取得と疎通(`device` マーカー)

## 実装の順序

1. Phase 0: 実機の疎通、無料版の範囲、1ゲームの手動プレイ、ルールの書き起こし(ここで素材が揃わなければ中止判断)
2. 設計の見直し(本書の「未確認」を埋める)と docs の追記
3. logic(盤とカードのデータ → ルール → 自己プレイ → 戦略)
4. vision(記録 → テンプレート → 認識 → 評価セット)
5. executor と実機の1手
6. 通しの自動プレイと KPI の測定

## セキュリティ考慮事項

- 端末の削除・データ消去の操作はコードに入れない。`adb` は必ず `-s <シリアル>`
- 「完全版を入手」などの購入・ストアへ移る操作はしない。禁止画面として扱う
- アプリ内の統計が変わる対局の開始は、最初の1回の前にユーザーへ確認する
- ゲーム画面やAPKをコミットしない(`assets/`、`datasets/`、`runs/`、`apk/` は Git 管理外)

## パフォーマンス考慮事項

- 1手の目安は平均30秒以内(KPI)。思考の持ち時間は設定で持つ(初期値は Hive と同じ5秒)
- モンテカルロの1試行は logic だけで回る。試行回数は持ち時間で決まるので、`apply` を軽く保つ(状態は不変の小さなデータクラス)

## 将来の拡張性

- 完全版の任務・難易度・部屋は、JSON の追加と設定の切り替えで足せる構造にする
- 戦略の強化(試行の中の方針の改良、重みの調整)は `strategy.py` と `strategy.toml` に閉じる
