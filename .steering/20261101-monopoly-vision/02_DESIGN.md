# 設計書

## アーキテクチャ概要

既存の Kahuna の方式に合わせる。`plugins/monopoly/vision/` に画面判別と読み取りを置き、`logic/` は画面に依存させない。読み取りは共通の `ElementReader`(テンプレートマッチング)を使う。

```
plugins/monopoly/
├── logic/          (既存: ルールと思考。画面に依存しない)
├── vision/         (新規)
│   ├── screens.py  画面の種類の判別(固定領域の色・テンプレート)
│   ├── log_reader.py  Log 行の読み取り(出目・着地・支払い)
│   └── templates.py  テンプレート画像の読み込み
└── data/           (新規)  テンプレート画像(小さい画像のみ。評価用の全画面は datasets/ に置く)
```

## コンポーネント設計

### 1. 画面の判別(vision/screens.py)

**責務**:
- 1 枚の画面(2432x1080)から、画面の名前と信頼度を返す
- 判別できない画面は「不明」を返す

**実装の要点**:
- Kahuna と同じく、固定位置の色とボタン文字のテンプレートで判別する
- 判別の順序は、排他が強いものから(ダイアログ → 拡大盤 → 通常盤)
- 盤の上の動く要素(駒、サイコロ、カメラ)は判別に使わない
- 手がかりは、評価セットの画像で確かめてから座標を決める(docs/05「画面の配置は操作して確かめてから」に準ずる)

### 2. Log 行の読み取り(vision/log_reader.py)

**責務**:
- Log の表示範囲から、行ごとの文字列を切り出す
- 既知の文型(`X rolled N` / `X landed on Y` / `X paid ₼N in rent to Y` など)に照合して、イベントに変換する

**実装の要点**:
- 文型は固定。単語ごとのテンプレート(`rolled`、`landed on`、`paid`、`in rent to`、数字)で照合する
- 固有名(マス名、プレイヤー名)は、盤のマス名リストから選ぶ(自由な文字列を作らない)
- 数字は 0〜9 のテンプレートで読む。桁が揃わなければ「不明」
- 読み取りは行単位。行が切れていたら「不明」(Phase 0 の結論: 行の切り出しは不安定。切れた行は読まない)

### 3. テンプレート読み取り(既存 toolkit/template_reader.py)
- 既存の `TemplateReader` を使う。新規の読み取り手段は作らない
- 信頼度の閾値未満は「不明」

## データフロー

### 画面判別
```
1. ScreenSource.capture() で画面を取る
2. screens.classify(image) で画面名と信頼度を得る
3. 信頼度 < 閾値、または「不明」なら、Recognition.state を None にして停止候補にする
```

### 出来事の読み取り(1 手番)
```
1. 画面を取る(Log の表示範囲を開いた状態)
2. log_reader.read_lines(image) で行ごとの文字列(または不明)
3. 既知の文型へ照合 → イベント列(出目、着地、支払い)
4. 不明の行があれば、その手番の読み取りを不確かとして記録
```

## エラーハンドリング戦略

### カスタムエラークラス
- 既存の `bglm.core.errors` を使う。新規クラスは作らない

### エラーハンドリングパターン
- 判別・読み取りの失敗は例外にせず、「不明」として返す
- 「不明」が連続したら、安全装置が停止する(既存の SafetyGuard の枠。本計画では不明の回数を返すところまで)

## テスト戦略

### ユニットテスト
- `vision/screens.py`: 参照画像ごとの正しい画面名(評価セット。Git 管理しない)
- `vision/log_reader.py`: 合成画像(文字を描いた小さな画像)で、文型の照合と「不明」の経路
- 期待値は、画面に見えている内容から手で書く(実装の出力を貼らない)

### 統合テスト
- 録画画像の並びを使い、画面判別と読み取りを通す(正常系と不明の経路)

### 認識の評価
- 変更前後で `bglm eval` 相当の結果を比べ、下がった要素が無いことを確かめる

## 依存ライブラリ

新規の依存は追加しない(opencv-python、numpy は既存)。OCR は使わない(Phase 0 で不安定を確認済み。導入は別計画)。

## 実装の順序

1. 参照画像を集める(2026-11-01 の対局のスクリーンショットから、画面の種類ごとに1枚以上)
2. 画面の種類ごとの手がかり(色・テンプレート)を決め、判別器を作る
3. 判別器を参照画像で検証し、誤判別が無いことを確かめる
4. Log の文型テンプレートを作る(単語と数字)
5. Log 行の読み取りを作り、合成画像と実機の画像で検証する
6. 出来事のイベント化(出目、着地、支払い)

## セキュリティ考慮事項

- adb は `-s <serial>` で呼ぶ(docs/05「外部操作」)。本計画は画面取得のみで、入力は送らない

## パフォーマンス考慮事項

- 判別は全画面を走査せず、判別の順序で早く抜ける
- テンプレートは起動時に 1 回読み込む

## 将来の拡張性

- 所持金の読み取り、盤上の駒位置の読み取りは、別の読み取り手段(OCR、VLM)を `toolkit/` に追加して差し替える
- 取引・建設・抵当の操作は `executor` に追加する(別計画)
