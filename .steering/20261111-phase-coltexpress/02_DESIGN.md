# 設計書

> 事実の正本は `RESULT.md`(実機とルールブック)。本書は「何をどの部品に持たせるか」を決める。確かめていないものは「未確認」と明記し、Phase 0 の続きで埋める。

## アーキテクチャ概要

Kahuna・Hive・Maquis と同じ。`GamePlugin` の実装を `plugins/coltexpress/` に足し、共通基盤は触らない。`application` は `PluginRegistry` が設定のゲーム名から動的に読み込む。

```text
plugins/coltexpress/
├── __init__.py          # create_plugin()。組み立てと公開だけ
├── logic/               # 画面に依存しない
│   ├── models.py        # Spot(車両, 階), Bandit, Loot, ColtState, 手(下の表)
│   ├── train.py         # 車両の並び、隣接、屋根の距離、視線
│   ├── cards.py         # 行動カード、各自の山札・手札・弾(既知と不明の枚数)
│   ├── rounds.py        # ラウンドカード(ターンの種類の並び、イベント)
│   ├── rules.py         # 計画・実行の合法手、手の適用、diff
│   ├── actions.py       # 6 種の行動の解決(対象の列挙と効果)
│   ├── marshal.py       # 保安官との遭遇(中立の弾、屋根へ逃げる)
│   ├── characters.py    # 6 人の能力
│   ├── events.py        # イベント 8 種
│   ├── scoring.py       # 得点、ガンスリンガー、同点
│   ├── belief.py        # 隠れた情報の標本化(相手の手札、裏向きのカード、財布の額)
│   ├── opponents.py     # 相手の方針の模型(模擬と自己対戦で使う)
│   ├── evaluation.py    # 局面の評価値
│   ├── strategy.py      # 計画・実行の手の選択(無作為化した試行)
│   └── simulation.py    # 自己対戦(1 ゲーム完走)
├── vision/
│   ├── layout.py        # 固定の領域(上段、左上の山、左下のターン、手札、ボタン)、禁止領域
│   ├── screens.py       # 画面種別
│   ├── hud.py           # 弾、財布・宝石・金庫の数、自分の所持金、手番、スタートプレイヤー
│   ├── turn_track.py    # ラウンド数、フェイズ、ターンの並びと現在のターン
│   ├── hand.py          # 手札の種類と枚数、ドラッグの開始位置
│   ├── played_cards.py  # 左上の山(種類、出した人、裏向き)
│   ├── train_view.py    # 映っている車両の検出と、車両ごとの座標系
│   ├── tokens.py        # 盗賊・保安官・略奪品の位置
│   ├── prompts.py       # 選択待ちの印(矢印・弾・略奪品)の検出
│   ├── recognizer.py    # 前の状態と照合して ColtState にする
│   └── executor.py      # 手 → ドラッグ / タップ、結果の確認
└── data/
    ├── action_cards.json   # 10 枚の内訳(出典つき)
    ├── cars.json           # 車両ごとの略奪品(出典つき)
    ├── round_cards.json    # ラウンドカードと駅(出典つき)
    ├── loot.json           # 財布の額の分布、宝石、金庫
    ├── strategy.toml       # 評価の重み、試行回数
    └── templates/          # 画面判別、印、数字
```

## 最初に決める設計上の論点

### 1. 手の単位: 1 操作 = 1 手

| フェイズ | 手 | 操作 | 出典 |
|---|---|---|---|
| 表示 | `Acknowledge` | ラウンドカード・フェイズの表示をタップで閉じる | `RESULT.md` §2 |
| 計画 | `PlayCard(kind)` | 手札のカードを上へドラッグ | p.3 |
| 計画 | `PlayCardFaceDown(kind)` | ゴーストの最初のターンだけ(操作は未確認) | p.5 |
| 計画 | `DrawCards` | 3 枚引くボタンをタップ | p.3 |
| 実行 | `MoveTo(car)` | 行き先の印をタップ | p.4 |
| 実行 | `Shoot(target)` | 相手の頭上の印をタップ | p.4 |
| 実行 | `Rob(loot_kind)` | 略奪品の印をタップ | p.4 |
| 実行 | `Punch(target)` → `DropLoot(loot_kind)` → `Knock(direction)` | 順と印は未確認(`RESULT.md` §4-3) | p.4 |
| 実行 | `MoveMarshal(direction)` | 未確認 | p.4 |

- 階の移動は選択が無いので手にしない(アプリが自動で解決する)。選択肢が 1 つでも印が出る場面(移動で確認済み)は、手として扱う
- 加速のターン(各自 2 回)は、同じ手番に計画の手が 2 つ続く。状態に「このターンの残り回数」を持つ
- 状態は実行フェイズの途中も持つ: 場のカード列の何枚目を解決中か、殴打の途中の段階

### 2. 隠れた情報

| 分からないもの | 扱い |
|---|---|
| 相手の手札・山札 | `cards.py`: 各自の 10 枚 + 受けた弾から、表向きに出された分を引いた多重集合。手札の枚数は数える(6 枚 − 出した数 + 引いた数 × 3。ドクは 7) |
| 裏向きのカード(トンネル、ゴースト) | 出した人と「不明」を場の列に持つ。実行フェイズで表になったら確定する |
| 財布の額 | `loot.json` の分布(250〜500$。内訳は未確認)。自分が取った財布は、所持金の差で額が分かる。相手の財布は期待値で数える |
| 自分の山札の順 | 残りの多重集合から無作為 |
| 相手のカードを読み損ねた | その 1 枚を「不明」として場の列に置く(推測で埋めない)。実行フェイズで表になるので確定できる |

`belief.py` は、上の制約に合う標本(相手の手札、裏向きのカード、財布の額)を 1 組作る。重み付け(相手の癖)は最初は入れない。

### 3. 思考

盤面は小さいが、相手 3 人の選択と隠れた情報で分岐が広い。探索木は作らず、**無作為化した試行の平均**で 1 手を選ぶ。

1. 候補の手ごとに、`belief` から標本を引く
2. ラウンドの残り(計画の残りターン → 実行)を、`opponents.py` の方針(相手)と軽い方針(自分の残りの手)で最後まで模擬する
3. ラウンドの終わりの局面を `evaluation.py` で評価し、候補ごとの平均が最も高い手を返す

- 実行フェイズの選択も同じ仕組みで、残りのカード列を模擬して選ぶ(場の列は既知が多いので、ここは精度が高い)
- `opponents.py` の最初の版は規則ベース(略奪品のある場所で強奪、同じ場所に相手がいれば殴打、撃てる相手がいれば射撃、など)。アプリの AI を観測して直す
- 評価値(初期案。重みは `strategy.toml`): 自分の所持金の期待値 − 相手の最大の所持金の期待値、ガンスリンガーの見込み(撃った数の差 × 1000$ の按分)、受けた弾の数(手札の詰まり)、金庫・宝石までの距離、保安官との距離、最終ラウンドは順位そのもの
- 選んだ手の**先頭の 1 手だけ**を返し、次の `choose` で実際の画面から選び直す(King & Assassins と同じ)

### 4. 予測と実際の盤面の差(`Rules.apply` と `diff`)

- 自分の計画の手は確定的(手札が減り、場の列に 1 枚足される)。`DrawCards` は引く 3 枚が不明なので、`diff` は手札の枚数だけを比べる
- 相手の手番と、実行フェイズの相手の行動は、`apply` で予測しない。`apply` は「相手の進行を待つ」印を立てた状態を返し、`diff` はその間の変化を差異として数えない
- 代わりに `recognizer` が、**相手のカード 1 枚ごとに「合法な解決で説明できる変化か」を確かめる**(場の列の次のカード、行動した人、上段の数の変化、映っている範囲の盗賊の位置)。説明できなければ止まる
- 共通基盤の変更は不要と見ている(Kahuna・Maquis・King & Assassins と同じ考え方)

### 5. カメラが動く盤の読み方

列車の映る範囲と倍率が場面で変わる(`RESULT.md` §2、§4-1)。固定の座標で盗賊を読めない。2 つを組み合わせる。

1. **論理側の追跡を主にする**: 盤面は、開始時の配置(ルールで決まる)から、解決されたカードと選択を `rules.apply` でたどれば分かる。画面は「追跡の照合」に使う
2. **車両を見つけてから相対の位置で読む**(`train_view.py`): 車両の屋根と台車の形をテンプレートで探し、倍率と各車両の枠を出す。機関車(または最後尾)が映っていれば、車両の番号が決まる。映っていなければ、追跡中の盤面と最もよく合う並びを採る(合うものが 1 つでなければ、その画面では照合しない)
3. 枠の中で、盗賊は服の色(ドク = 水色、トゥーコ = 赤、ベル = 紫、ジャンゴ = 黒 など)、略奪品は床の絵と数字、保安官は黄の服で読む
4. **列車全体が映る場面(ラウンドの変わり目など)で、全盗賊の位置を照合する**。食い違えば止まる。全体が映る場面を自分から作れるか(ピンチなど)は未確認で、作れるなら自分の手番の前に毎回照合する
5. 上段の表示(弾、略奪品の数、所持金)は固定の位置なので、毎回読んで追跡と比べる

再開のとき(前の状態が無い)は、全体が映る画面が取れるまで待ち、取れなければ止まる。山札の中身は「不明」から始める。

### 6. 認識の手段

- 画面種別: 固定位置のテンプレート(メニューの題字、「プレイ」、「キャラクターを選ぶ」、ラウンドカードの枠、左下のフェイズの文字、「あなたの番」、一時停止の題字)
- 手番: 上段の輪の大きさ(自分の輪が大きい)と、3 枚引くボタンの明るさ。両方が合うときだけ自分の手番とする
- 数字(弾 x N、略奪品の数、所持金、ラウンド n/5): 桁のテンプレート(Monopoly・Maquis と同じ作り)
- 手札: カード上端の印(↔、↕、$、銃、拳、星)のテンプレート。重なった同種の枚数の読み方は未確認で、読めなければ「出した数と引いた数」からの計算を正とする
- 場のカード: 左上の山の一番上の印と枠の色。相手の手番中は約 1 秒ごとに取得し、変化を 1 枚として数える。取りこぼしは、ターンの進み(左下)と手番の移りから検出する
- 選択の印: 明るい印(矢印・弾・略奪品)をテンプレートで探す。灰色の印は対象外。**logic の合法な選択肢と、画面の印の数・種類が一致するかを照合する**(食い違えば止まる)
- VLM は使わない

### 7. 操作の安全

確認の無い操作が多い(`RESULT.md` §5)。executor は 1 手ごとに次の順で動く。

1. 画面種別と自分の手番を確かめる(違えば送らない)
2. 対象(カードの印、選択の印)の位置を、その画面で検出する(固定の座標を使わない。ボタンと表示を閉じるタップだけは固定)
3. 入力を 1 つ送る
4. 画面を取り直し、期待した変化(手札が 1 枚減る、場の山に自分のカードが載る、手番が移る、印が消える)を確かめる。変化が無ければ、再実行せずに止まる

- ドラッグの終点は盤の中央付近とし、上段の輪・左上の山・右上の領域に入れない
- 禁止領域(`layout.py`): メニューの「他のゲーム」と右上の印、クラシックの「ゲームに参加」と切り替え、「オンラインで遊ぶ」、一時停止の「メニューへ」。executor がタップを拒否する
- 前面のパッケージが変わった、または未知の画面なら、入力を送らず止まる
- 対局の開始(メニュー → クラシック → ゲームを作る → プレイ → キャラクターの決定)と終局後の後始末は、自動の実行ループに入れず、`scripts/coltexpress/` の道具に置く(King & Assassins の「GOOD GAME」と同じ扱い。終局の画面は未確認)

## コンポーネント設計

### Rules(`logic/rules.py` ほか)
**責務**: フェイズごとの合法手、手の適用、イベント、得点(`outcome` は自分の順位から "win" / "lose")、`diff`。
**要点**: 行動の解決は `actions.py`、能力は `characters.py`、イベントは `events.py` に分ける(1 ファイル 300 行以下)。カード・車両・ラウンドカードは JSON に置き、出典(ルールブックのページ、または実機の画像名)を書く。相手の手も同じ `apply` で解決できるようにし、模擬と追跡で共用する。

### Strategy(`logic/strategy.py`、`evaluation.py`、`belief.py`、`opponents.py`)
**責務**: 合法手から 1 手を選ぶ。
**要点**: 持ち時間の中で試行回数を決める。乱数は `random.Random` を引数で受ける。状態は不変の小さなデータクラスにして、`apply` を軽く保つ。`Acknowledge` しか無い場面は思考を通さずに返す。

### Recognizer(`vision/recognizer.py`)
**責務**: 画面 → `ColtState` と `UiState`。相手の進行中は落ち着き(自分の手番、選択待ち、表示)を `toolkit/waiting.poll` で待ち、その間の場のカードを集める。前の状態と照合し、信頼度が足りなければ止まる。
**要点**: 入力は送らない。相手のカードの解決を `rules.apply` でたどって盤面を進める。

### MoveExecutor(`vision/executor.py`)
**責務**: 手をドラッグ・タップに変換し、実行後の画面で結果を確かめる(上の「操作の安全」)。
**要点**: ドラッグは `input swipe`(開始 = カードの印の下、終点 = 盤の中央、600ms)。共通の接続にドラッグの口が無ければ、インターフェースの不足として記録する(Monopoly の Log 読みで保持付きドラッグを使った実績があるので、あると見ている。実装前に確かめる)。

## データフロー

```text
1. 画面取得(adb) → 画面種別。対局以外・禁止画面なら停止
2. 相手の進行中なら待つ(場のカードを集め、盤面の追跡を進める)
3. 上段・ターン・手札・場・映っている列車を読み、追跡と照合して ColtState を作る
4. Rules.legal_moves → Strategy.choose(持ち時間)
5. MoveExecutor が 1 操作 → 画面の変化で確認 → ログ保存
6. 次の認識で、予測との差を確かめる
7. 終局の画面を検出したら停止(順位と金額を記録)
```

## エラーハンドリング戦略

- 新しい例外クラスは作らない。`core/errors.py` の既存の例外と、`Recognition.low_confidence`、`ExecutionResult(success=False, reason=...)` で表す
- 想定外の画面、信頼度不足、禁止画面、合法手が 0、追跡と画面の食い違い(盗賊の位置、上段の数)、選択の印と合法な選択肢の食い違い、手札の枚数の食い違い — いずれも入力を送らず停止する
- 操作後に期待した変化が無ければ、再実行ではなく停止して画面を保存する

## 実装の順序

1. Phase 0 の続き: 4 人戦を手で終え、`RESULT.md` §4 を埋める。カード・車両・ラウンドカードの表を作る(カメラの扱いが決まらなければ中止判断)
2. 設計の見直し(本書の「未確認」を埋める)
3. logic(データ → 行動・能力・イベント → 自己対戦 → 戦略)
4. vision(記録 → テンプレート → 固定の領域の認識 → 列車の認識 → 評価セット)
5. executor と実機の 1 手(`scripts/common/step_once.py --game coltexpress`)
6. 通しの自動プレイと KPI の測定(4 人、ジャンゴ)
7. 他のキャラクター、他の人数

## セキュリティ考慮事項

- 端末の削除・データ消去の操作はコードに入れない。`adb` は必ず `-s <シリアル>`
- オンライン、ログイン、宣伝は押さない。ログインした状態を検出したら、対局を始めずに止まる(右上の人物の印を確かめる。印の意味は未確認)
- ゲーム画面、APK、ルールブックの PDF をコミットしない

## パフォーマンス考慮事項

- 1 手の目安は平均 30 秒以内(KPI)。1 ゲームは 5 ラウンド × 4〜5 ターンで、自分の操作は計画 約 22 手 + 実行の選択 + 表示を閉じる 10 回ほど
- 相手の進行中は約 1 秒ごとに画面を取る(1 回 0.7〜1.2 秒の実測に近い)。相手のカードの取りこぼしは「不明」で受ける
- 思考の持ち時間(初期値): 計画 5 秒、実行の選択 2 秒
