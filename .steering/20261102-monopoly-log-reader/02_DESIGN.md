# 設計書

## アーキテクチャ概要

`plugins/monopoly/vision/` に `dice.py`(出目)と `log_reader.py`(Log の行)を追加する。数字は計画 1 の桁テンプレートを再利用してよい(同じ字体かは、観察で確かめる)。

```
plugins/monopoly/
├── vision/
│   ├── dice.py          (新規) 黄色の表示から、プレイヤー名と出目
│   ├── log_reader.py    (新規) Log の行 → 文型照合 → イベント
│   └── events.py        (新規) 読み取り結果のデータ型(画面にも logic にも依存しない純粋な型)
└── data/
    ├── words/           (新規) 語彙(プレイヤー名、動詞、マス名、カード文面)のテンプレート
    └── digits/          (計画 1)
datasets/eval/monopoly/log/  (新規、Git 管理外) 画像 + labels.json
```

出来事の型 `events.py` は、`logic` から import できる位置に置く(`logic/events.py`)。`logic` は `vision` を import できないため、型は `logic` 側に定義し、`vision` が生成する。

## 読み方の決定(最初に画像で確かめる)

どの経路で何を読むかは、観察の結果で決める。設計は次の順に判断する:

1. 黄色の表示に出目が出るか(自分の手番、AI の手番、ゾロ目の 2 回目、刑務所の最中)。出る時間(何ミリ秒)と、位置
2. Log パネルの文字の色と縁。パネルが透けるが、文字が白などの一定色なら、色の条件と縁の有無で分けられる可能性がある
3. Log の「上段だけ読める」範囲で、直近の出来事が見えるか(新しい行の位置)

1 が安定すれば、出目は黄色の表示だけで取る。Log の行は、カード・刑務所・AI の購入のような、他に取れない情報にだけ使う。

## コンポーネント設計

### 1. `dice.py`
- 黄色の画素を抜き(色の条件は観察で決める)、連結成分に分ける
- 末尾から、数字の成分(1〜2 桁)を読む。プレイヤー名は、先頭の成分の並びをテンプレート(2 名分)に照合する
- 成分が想定外(数、並び)なら不明。表示が無ければ「なし」(黄色の成分が閾値未満)
- 出目の範囲は 2〜12。範囲外は不明にする(誤読の検出)

### 2. `log_reader.py`
- Log パネルの表示範囲から行を切り出す。切り出しは、文字の色の条件(観察で決める)で、輝度の閾値は使わない
- 行を単語に分け(語間の空白)、語彙のテンプレートで 1 語ずつ照合する
- 語の並びを文型に照合してイベントにする。文型は固定の一覧(下記)で、一覧に無い並びは不明
- 数字は、`digits/` のテンプレート。桁が揃わなければ不明
- 行が切れていたら不明(Phase 0 の結論)

### 3. 文型(初期。収集した Log で確定する)
- `{player} rolled {N}`(`doubles` の有無)
- `{player} landed on {square}`
- `{player} bought {square} for {amount}` / 落札の行
- カードの引き: `{player} drew ...`(文面は語彙)
- 刑務所: `{player} went to jail` / `posted bail` / `rolled doubles and got out`
- GO の受け取りは Log に出ない。所持金の差分で扱う(計画 3)

### 4. 語彙の管理
- 語彙は、収集した画像から切り出して増やす。`words/` に、語ごとの画像を 1〜複数
- 語が足りない行は不明を返す。不明の行は、画像を保存して語彙を増やす入力にする(計画 3 の実行ログと連携)

## データフロー

```
黄色の表示:  画面 → dice.read_dice(frame) → DiceReading(player, total, doubles | None | 不明)
Log の行:    画面(Log 表示中) → log_reader.read_lines(frame) → list[LogLine(event | 不明)]
```

## エラーハンドリング戦略
- 例外にしない。不明を返す
- 「なし」(表示が無い)と「不明」(あるが読めない)を型で分ける

## テスト戦略

- ユニット: 合成画像(語彙のテンプレートを並べた行)で、文型照合・不明・切れた行の経路。期待値は手で書く
- 評価: 実機の画像の評価セット(別の局で集める)で、誤読 0 を確認する(`scripts/monopoly/eval_log.py`)
- 汎化: 語彙のテンプレートを切り出した局と、評価の局を分ける

## 実装の順序

1. 画像を集める(読み取り専用。局の進行に合わせ、黄色の表示と Log を複数回)
2. 観察して、読み方を決める(上の 3 点)
3. 出目(`dice.py`)を作って評価する。これだけで計画 3 の最初の縦通しは動く
4. Log の行(`log_reader.py`)を作って評価する

## 受け入れ条件を満たさなかった場合
- 出目の誤読が 0 にならなければ、原因を `RESULT.md` に書き、別の読み取り手段を別計画にする。誤読を許容して先へ進まない
- Log の行が語彙の不足で読めない割合が高い場合は、読める文型だけを `logic` へ渡し、残りは不明として計画 3 の停止・記録に任せる(これは失敗ではなく、方針の範囲内)

## セキュリティ考慮事項
- 画面取得のみ。`adb` は `-s 355092380222016` を付ける
- 画像は `datasets/` に置く(Git 管理外)

## パフォーマンス考慮事項
- 黄色の表示は一瞬しか出ない可能性がある。読み取りは 1 枚あたり数十 ms に収める(取得間隔を詰められるように)
