# 設計書

> 事実の正本は `RESULT.md`(実機)。本書は「何をどの部品に持たせるか」を決める。確かめていないものは「未確認」と明記し、Phase 0 の続きで埋める。

## アーキテクチャ概要

Kahuna・Hive と同じ。`GamePlugin` の実装を `plugins/jaipur/` に足す。`application` は `PluginRegistry` が設定のゲーム名から動的に読み込む。共通基盤の変更は 1 点だけ見込む(OCR の共有。論点 6)。

```text
plugins/jaipur/
├── __init__.py          # create_plugin()。組み立てと公開だけ
├── logic/               # 画面に依存しない(BoardGameAI の game/・ai/ を写して直す。01 の「流用の範囲」)
│   ├── models.py        # CardType、手(TakeOne / TakeCamels / Exchange / Sell / Acknowledge)、JaipurState、UiPhase
│   ├── ruleset.py       # 札の枚数、トークンの値、手札の上限、最低売却枚数、先取数(data/ruleset.json を読む)
│   ├── actions.py       # 合法手の列挙と検査                      ← bgai/game/actions.py
│   ├── engine.py        # 全情報の状態、準備、手の適用、ラウンドの終了と勝者  ← bgai/game/state.py、engine.py
│   ├── knowledge.py     # 公開情報の追跡(Knowledge、PublicEvent)     ← bgai/game/tracker.py、view.py
│   ├── inference.py     # 画面の読み取りの前後から、相手の手を PublicEvent にする(新規)
│   ├── bar_text.py      # 確定バーの文言 ↔ 手(文字列の組み立てと解析。新規)
│   ├── determinize.py   # 見えている情報と矛盾しない全情報の状態を 1 つ作る   ← bgai/ai/determinize.py、game/search_state.py
│   ├── rollout.py       # プレイアウト方策                          ← bgai/game/rollout.py(葉の評価は出所を確かめてから)
│   ├── ismcts.py        # 探索                                    ← bgai/ai/ismcts.py
│   ├── rules.py         # Rules(legal_moves / apply / is_terminal / outcome / diff)
│   ├── strategy.py      # Strategy(持ち時間で ISMCTS を回す)
│   └── simulation.py    # 自己対戦(1 マッチ完走)
├── vision/
│   ├── layout.py        # 固定の領域(市場 5 枠、トークンの列、群れ、袋、山札、バー、進行役、吹き出し)、禁止領域
│   ├── screens.py       # 画面種別
│   ├── market.py        # 市場 5 枠の札(空きを含む)
│   ├── hand.py          # 自分の手札(枚数ごとの位置)、選択中(橙色)の札
│   ├── counters.py      # 群れ、相手の手札の枚数、得点、山札の残り
│   ├── tokens.py        # 商品トークンの山(一番上の値、残数)、ボーナストークンの残数
│   ├── bar.py           # 確定バーの有無、字の色(白 / 黄)、文言(OCR)
│   ├── replay.py        # 進行役を押して相手の直前の手を再生し、取った札などを読む
│   ├── board_reading.py # 1 枚の画面 → ScreenReading(上の読み取りをまとめ、整合を確かめる)
│   ├── recognizer.py    # 前の状態と照合して JaipurState にする
│   └── executor.py      # 手 → タップ列、バーの照合、確定、結果の確認
└── data/
    ├── ruleset.json     # 枚数とトークンの値(出典つき)
    ├── strategy.toml    # 探索の設定(反復の上限、c_uct、プレイアウトの無作為の割合)
    └── templates/       # 画面判別、札、数字
```

## 最初に決める設計上の論点

### 1. 手の単位: 1 手 = 選択のタップ列 + 確定

| 手 | 操作 | 確定の前の照合(バー) |
|---|---|---|
| `TakeOne(good)` | 市場のその種類の枠を 1 回タップ → バー | 「TAKE ONE <種類>」(確認済み) |
| `Sell(good, count)` | 手札のその種類を 1 枚タップ(同種がまとめて選ばれる)→ `count` が手持ちより少なければ、余りを 1 枚ずつタップして外す → バー | 「SELL <n> OF <種類>」(確認済み) |
| `TakeCamels()` | 未確認(市場のラクダをタップ?) | 未確認 |
| `Exchange(take, give)` | 未確認(市場の取る札と、手札・ラクダの出す札を選ぶ?) | 未確認 |
| `Acknowledge(kind)` | 吹き出しの矢印をタップ / ラウンド終了の表示を進める(後者は未確認) | — |

- 確定の前は取り消せる(`RESULT.md` §2)ので、選択の途中で何かが食い違ったら、選択を外して止まる。盤面は変わらない
- 手札のタップが「同種をまとめて選ぶ」ため、交換で同じ種類の一部だけを出す手は、外すタップが要る。交換の選び方は Phase 0 の続きで確かめてから、タップ列の作り方を決める
- `Acknowledge` しか無い場面は、思考を通さずに返す

### 2. 状態と隠れた情報

`JaipurState` は、追跡している知識(`Knowledge`)と画面の段階(`UiPhase`)を持つ不変のデータ。

| 分からないもの | 扱い |
|---|---|
| 相手の手札 | 枚数は数える。市場から取った札は種類まで分かる(`opp_known`)。残りは「山札と相手の手札に残る札の内訳」(`unseen`)から無作為に定める |
| 山札の並び | `unseen` の残りを無作為に並べる |
| 相手のボーナストークンの値 | 区分(3 / 4 / 5 枚)ごとの、まだ見ていない値から無作為。自分の分の値が画面で見えるかは未確認(見えなければ、自分の分も同じ扱いにし、得点の表示から逆算できるかを確かめる) |
| 自分の補充の札(見逃したもの) | 次の画面の市場から分かる。相手がその札を取ったときは、論点 3 の推定で扱う |

`Knowledge` の不変条件(`unseen` の合計 = 山札 + 相手の手札の不明分、負の枚数が無い、など)は `BoardGameAI` の `KnowledgeTracker._check` を引き継ぐ。破れたら止まる。

### 3. 相手の手の推定(`logic/inference.py`)

自分の確定から次の自分の手番までに起きるのは「自分の手の補充 → 相手の手 1 つ → その補充」。相手の手は予測しない。

1. 自分の手を適用した後の知識から、相手の手の候補を「公開される形」で列挙する(1 枚取る × 種類、ラクダを全部取る、売る × 種類 × 枚数、交換 × 取る札 × 出す札)
2. 候補ごとに、次の安定した画面(市場の種類別の枚数、相手の手札の枚数、相手の群れ、山札の残り、トークンの山、ボーナストークンの残数)と合うかを確かめる
3. 合う候補が、知識に与える効果で 1 つに決まれば採る。**効果の違う候補が 2 つ以上残るときだけ、進行役の再生(`vision/replay.py`)で確かめる**。再生でも決まらなければ止まる。合う候補が 0 なら止まる

- 市場は「取った枠に補充される」(確認済み)ので、取った種類と補充の種類が同じだと画面が変わらない。この場合が 3 の「再生で確かめる」に当たる
- 再生の読み方(取った札の小さい絵と矢印。売る・交換の表示)は、1 枚取る以外が未確認
- 再生は盤面を変えない操作(確認済み)なので、`recognizer` から送ってよい入力とする(Maquis の `deck_reader` と同じ扱い)。`recognizer` が送る入力は、進行役の長押しだけに限る
- ラウンドの開始で相手が先手のときは、最初の画面がすでに相手の手の後でありうる(相手の手札 + 群れ ≠ 5、または山札 ≠ 40)。このときも再生で手を確かめ、確かめられなければ止まる。開始時の進み方は未確認

### 4. 予測と実際の盤面の差(`Rules.apply` と `diff`)

- `apply` は、自分の手で確定する部分だけを進める(手札、群れ、取った札が抜けた市場、売ったときのトークンの山)。補充の札と相手の手は「待ち」の印にし、`diff` はそこを比べない
- `diff` が比べるのは、自分の手札・自分の群れ・自分が取ったトークンの数・市場のうち補充されない枠
- 相手の手は論点 3 で、合法な手で説明できるかを確かめる

### 5. 思考

- `BoardGameAI` の ISMCTS(Single-Observer、ネットなし)を写す。葉の評価はプレイアウトで始める
- 持ち時間(初期値 5 秒)で打ち切る。`BoardGameAI` の実測では、1360 反復で 1 手 約 3 秒
- **強さの見込み(リスク)**: `BoardGameAI` の測定(PC 上、移植 CPU 相手)では、プレイアウトだけの探索は MEDIUM 相当に 0.98、HARD 相当に 0.37、EXPERT 相当に 0.26。評価関数を葉に混ぜた版は HARD 相当に 0.65。アプリの難易度 3〜4 に勝ち越すには葉の評価が要る。流用できない場合は、ルールから自前の評価(残りのトークンの値、手札の売却見込み、ラクダの差)を書き、自己対戦で比べる
- アプリの難易度 1〜4 と、`BoardGameAI` の言う EASY〜EXPERT の対応は、本プロジェクトでは実機の勝率で確かめる(推測で書かない)

### 6. 認識の手段

- 画面種別: 固定位置のテンプレート(メニューの題字、設定の「PLAY」、吹き出しの枠、バー、ラウンド終了の表示)
- 市場: 5 枠が固定。枠ごとに 7 種の札のテンプレートと「空き」を比べる
- 手札: 枚数ごとに札の位置が変わる。枚数ごとの位置表を Phase 0 の続きで作り、各位置の色で種類を読む。手札は追跡でも分かるので、画面は照合に使う(食い違えば止まる)
- 数字(群れ、得点、山札の残り、トークンの値): 桁のテンプレート(Monopoly・Maquis と同じ作り)。山札の残りは右端で切れているので、追跡(補充の数)を正とし、読めたときだけ照合する
- バーの文言: OCR(RapidOCR)で読み、`logic/bar_text.py` で手に解析する(誤読を許す解析は Monopoly の `events.py` と同じ考え方)。字の色が黄(合法でない選択)なら確定しない
  - RapidOCR のエンジンは今 `monopoly/vision/ocr_engine.py` にあり、プラグイン同士は import できない。`toolkit/ocr_reader.py`(`docs/04` に計画済み)へ移して両方から使う。**共通基盤の変更として記録する**
- 手番: 自分の手番かどうかは、市場の札をタップできる状態か(演出が終わり、吹き出しが無く、市場が 5 枚または山札切れ)で決める。手番を示す表示があるかは未確認
- VLM は使わない

### 7. 操作の安全

executor は 1 手ごとに次の順で動く。

1. 画面種別と、選択が何も無いこと(バーが無い)を確かめる
2. 対象の札の位置を、その画面の読み取りから決める(市場は枠、手札は枚数ごとの位置表)
3. 選択のタップを送り、取り直して、橙色の札が意図どおりかを確かめる
4. バーの字が白で、文言が意図した手と一致することを確かめる。違えば、選択を外して止まる
5. バーをタップして確定する
6. 取り直して、期待した変化(手札・群れ・トークン)を確かめる。変化が無ければ、再実行せずに止まる

- 禁止領域(`layout.py`): メニューの ACCOUNT・GAMES・CAMPAIGN・TUTORIAL・OPTIONS、PLAY A GAME の ONLINE DUEL・PASS & PLAY、対局中の左上の印。executor がタップを拒否する
- 前面のパッケージが変わった、または未知の画面なら、入力を送らず止まる
- 対局の開始(メニュー → SOLO → 難易度と先取数の選択 → PLAY)とマッチ終了後の後始末は、自動の実行ループに入れず、`scripts/jaipur/` の道具に置く

## コンポーネント設計

### Rules(`logic/rules.py` ほか)
**責務**: 自分の手番の合法手、手の適用、ラウンド・マッチの終了、`outcome`、`diff`。
**要点**: 合法手は `actions.py`、全情報の進行は `engine.py`。枚数とトークンの値は `data/ruleset.json` に出典つきで書く。アプリ独自の扱い(完全な同点の勝者、ラクダトークンを同点判定の枚数に数えるか、山札切れの終了の時点)は、`BoardGameAI` がデコンパイル結果から決めた値をそのまま書かず、**実機で観測できたものだけを確定とし、残りは公開ルールの記述に合わせて「未確認」と注記する**。

### Strategy(`logic/strategy.py`、`ismcts.py`、`determinize.py`、`rollout.py`)
**責務**: 合法手から 1 手を選ぶ。
**要点**: 乱数は `random.Random` を引数で受ける。持ち時間が尽きたら、根の訪問回数が最大の手を返す。合法手が 1 つなら探索しない。

### Recognizer(`vision/recognizer.py`)
**責務**: 画面 → `JaipurState`。相手の進行中は落ち着き(同じ読み取りが 2 回続く)を `toolkit/waiting.poll` で待つ。前の状態と `inference` で照合し、信頼度が足りなければ止まる。
**要点**: 送ってよい入力は進行役の長押しだけ。前の状態が無いとき(起動直後)は、ラウンドの開始の画面なら始められる。**ラウンドの途中からは、相手の手札の知識を「不明」にして始める**(売られた札の枚数はトークンの山の減りから数える。空の山があって数えられないときは止まる)。

### MoveExecutor(`vision/executor.py`)
**責務**: 手をタップ列に変換し、バーで照合してから確定し、結果を確かめる(上の「操作の安全」)。

## データフロー

```text
1. 画面取得(adb) → 画面種別。対局以外・禁止画面なら停止
2. 相手の進行中なら、落ち着くまで待つ
3. 盤を読み、前の状態からの差を inference で説明する(必要なら再生) → 知識を進めて JaipurState を作る
4. Rules.legal_moves → Strategy.choose(持ち時間)
5. MoveExecutor: 選択 → バーの照合 → 確定 → 画面の変化で確認 → ログ保存
6. 次の認識で、予測との差を確かめる
7. ラウンド終了の表示は Acknowledge で進め、次のラウンドの知識を作り直す。マッチ終了を検出したら停止(勝敗と得点を記録)
```

## エラーハンドリング戦略

- 新しい例外クラスは作らない。`core/errors.py` の既存の例外と、`Recognition.low_confidence`、`ExecutionResult(success=False, reason=...)` で表す(`BoardGameAI` の `TrackerInconsistencyError` などは、写すときに既存の例外へ寄せる)
- 想定外の画面、信頼度不足、禁止画面、相手の手を説明できない、知識の不変条件の破れ、手札の読み取りと追跡の食い違い、バーの文言の不一致 — いずれも入力を送らず(選択中なら外して)停止する
- 操作後に期待した変化が無ければ、再実行ではなく停止して画面を保存する

## テスト戦略

### ユニットテスト(`tests/plugins/jaipur/unit/`)
- logic: 4 種の手の合法性と適用、売却のトークンとボーナス、ラウンドの終了、ラクダトークン、勝者、マッチ。**期待値はルールの記述から手で作り、出典を書く**(`BoardGameAI` のテストは観点の参考にとどめ、期待値を写さない)
- logic: 追跡と全情報の視点の一致、`determinize` の標本が知識と矛盾しないこと、`inference`(1 つに決まる例、再生が要る例、説明できない例)、`bar_text` の往復と誤読
- logic: 固定シードの自己対戦で完走し、不正な手が出ない。探索が無作為の方針に勝ち越す
- vision: 合成画像と、記録した実画面(`datasets/eval/jaipur/`)。録画が無い環境は飛ばす
- vision: 禁止領域へのタップを executor が拒否する。バーが黄色い字・文言が違うとき確定しない

### 統合テスト(`tests/plugins/jaipur/integration/`)
- 記録画面でのドライラン、リプレイ

### 実機テスト(`tests/plugins/jaipur/device/`)
- 画面取得と疎通(`device` マーカー)

## 実装の順序

1. Phase 0 の続き: SOLO を手で 1 マッチ終え、`RESULT.md` §3 を埋める。設計の「未確認」を直す
2. logic(写す → 根拠の付け直し → テスト → 自己対戦 → 探索)。実機が要らないので、1 と並行できる
3. vision(記録 → テンプレート → 盤の読み取り → 相手の手の推定と再生 → 評価セット)
4. executor と実機の 1 手(`scripts/common/step_once.py --game jaipur`)
5. 通しの自動プレイと KPI の測定(難易度 1)
6. 難易度 2〜4、葉の評価の改良

## セキュリティ考慮事項

- 端末の削除・データ消去の操作はコードに入れない。`adb` は必ず `-s <シリアル>`
- ONLINE DUEL、ACCOUNT、GAMES は押さない。ログインした状態を検出する手段(ACCOUNT の画面)は対局の開始の道具で確かめ、ログイン済みなら始めずに止まる
- ゲーム画面、APK、アプリの XML、移植 CPU のコードをコミットしない

## パフォーマンス考慮事項

- 1 手の目安は平均 30 秒以内(KPI)。画面取得は 1 回 約 1 秒、1 手の取得は 4〜6 回(選択の確認、バー、確定の後、相手の手の後)
- 思考の持ち時間(初期値): 5 秒。反復の上限と下限は `docs/05`「パラメータ境界値の設計」に従って決める
- 1 ラウンドは双方で 20〜30 手、1 マッチは 2〜3 ラウンド

## 将来の拡張性

- 葉の評価と探索の設定は `rollout.py`・`strategy.toml` に閉じる
- 先取数(1〜3)は `ruleset` の値で受ける
