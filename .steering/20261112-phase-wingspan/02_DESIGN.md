# 設計書

> 事実の正本は `RESULT.md`(実機とルール)。本書は「何をどの部品に持たせるか」を決める。確かめていないものは「未確認」と明記し、Phase 0 の続きで埋める。Go / No-Go は 2026-11-13 に Go と判断した(`RESULT.md` §8)。

## アーキテクチャ概要

Kahuna・Hive と同じ。`GamePlugin` の実装を `plugins/wingspan/` に足す。共通基盤の変更は 1 点を見込む(OCR のエンジンを `toolkit` へ移す。論点 4)。`application` は `PluginRegistry` が設定のゲーム名から動的に読み込む。

```text
plugins/wingspan/
├── __init__.py            # create_plugin()。組み立てと公開だけ
├── logic/                 # 画面に依存しない
│   ├── models.py          # Food、Habitat、Nest、BirdCard、PlacedBird、PlayerBoard、Placement
│   ├── state.py           # WingspanState、決定(Task)、手(Move)
│   ├── cards.py           # 札の表(data/birds.json、bonus.json)の読み込みと検査。UnknownCardError
│   ├── board.py           # 列ごとの行動の強さ、卵のコスト、手番の数
│   ├── payment.py         # 餌の払い方の列挙(「/」、何でも、2 個で 1 個の交換)
│   ├── helpers.py         # 山札・ダイス・卵・餌の更新(乱数は state.seed から)
│   ├── powers.py          # 鳥の能力(AUTO / DECIDE / PINK。未実装の種類は効果なし)。種類が増えたら powers/ に分ける
│   ├── turn.py            # 行動の展開、決定ごとの合法手と適用、決定の自動整理(settle)
│   ├── rounds.py          # 手番の終わり、トレイの補充、ラウンドの終わり、先手の交代
│   ├── goals.py           # 目的タイル 16 種の数え方と採点
│   ├── bonus.py           # ボーナスカードの数え方
│   ├── scoring.py         # 最終得点、同点の判定
│   ├── rules.py           # Rules(legal_moves / apply / is_terminal / outcome / diff)
│   ├── setup.py           # 試験用の準備(自己対戦)
│   ├── belief.py          # 隠れた情報の標本化(山札と乱数の並びを取り直す)
│   ├── evaluation.py      # 局面の評価値
│   ├── strategy.py        # 手の選択(手番の貪欲な先読み × 標本)
│   └── simulation.py      # 自己対戦(1 ゲーム完走)と不変条件の検査├── vision/
│   ├── layout.py          # 固定の領域(菱形、顔、右の数、全体ボードの格子、右下の確定、左下の取り消し)、禁止領域
│   ├── screens.py         # 画面種別、表示の種類(生息地 / 全体ボード)、札の表示のタブ
│   ├── mat.py             # 全体ボード: 枠ごとの鳥、卵、蓄えた餌、差し込んだ札、白い枠(次の枠)
│   ├── card_reader.py     # 小さい札 1 枚 → 札名(OCR + 札の表との照合)、翼長・点での確認
│   ├── counters.py        # キューブ、卵(数/上限)、餌 5 種、ラウンドと残りの手番
│   ├── feeder.py          # 餌箱のダイスの目
│   ├── tray.py            # カードトレイ 3 枚、山札と捨て山の数(プレビュー)
│   ├── hand.py            # 手札の枚数、札ごとの位置、札名、ボーナスカード
│   ├── prompt.py          # 行動の枠と能力の案内: 文、選択肢、手順のタブ、確定・スキップ・取り消し、赤い印
│   ├── goals.py           # 目的と得点の画面
│   ├── recognizer.py      # 画面 → WingspanState。表示を全体ボードに揃える、相手のボードを見る
│   └── executor.py        # 手 → タップ / ドラッグ、結果の確認
└── data/
    ├── birds.json         # 鳥 180 枚(出典つき)
    ├── bonus.json         # ボーナスカード 26 枚
    ├── goals.json         # 目的タイル 16 枚
    ├── strategy.toml      # 評価の重み、試行回数
    └── templates/         # 画面判別、数字、ダイスの目、餌・巣・生息地の印
```

## 最初に決める設計上の論点

### 1. 手の単位: 1 操作 = 1 手、手番 = 決定の列

アプリは、行動を選んだ後に「何を選ぶか」を 1 つずつ聞き、最後に確定を押させる(`RESULT.md` §2)。logic も同じ形にする。状態に「いま答える決定(`Decision`)」を持たせ、合法手は「その決定への答え」とする。

| 決定 | 手 | 操作 | 確認 |
|---|---|---|---|
| 手番の開始の表示 | `StartTurn()` / `AckOpponentResult()` | 中央を押下。**相手の手番の結果の案内が出る場合は 2 回**(案内 → 「残り n 手番」→ 盤面)。1 回押すごとに画面を確かめる | 確認済み(`RESULT.md` §11) |
| 初期選択 | `ToggleKeep(item)` | 札・餌をタップ | 確認済み |
| 初期選択 | `ChooseBonus(card)` | 札をタップ | 確認済み |
| 行動を選ぶ | `PlayBird(card, habitat)` | 手札の札を枠へドラッグ(拡大は不要。生息地・全体ボードのどちらの表示でも置ける)。**複数の生息地の鳥は「プレイする生息地を選んでください」が出る** | 確認済み(`RESULT.md` §9〜§11) |
| 生息地を選ぶ | `ChooseHabitat(habitat)` | 生息地の印をタップ(既定の選択あり)→ 確定 | 確認済み(`RESULT.md` §11) |
| 行動を選ぶ | `GainFood()` / `LayEggs()` / `DrawCards()` | 全体ボードで、その行の白い枠をタップ | 確認済み |
| 支払い | `Pay(foods)` | 既定の払い方なら確定。違えば「変更」→ 餌を 1 個ずつタップ → 確定 → 要約で確定 | 確認済み(`RESULT.md` §9) |
| 餌を選ぶ | `TakeDie(die)`、`ChooseFace(food)` | ダイスをタップ、「1 つ選ぶ」をタップ | 確認済み |
| 卵を置く | `LayEggOn(slot)` | 鳥をタップ(1 個ずつ) | 確認済み |
| 卵を払う | `PayEggFrom(slot)` | 全体ボードの表示で鳥をタップ(1 個ずつ。生息地の表示では他の行を押せない) | 確認済み(`RESULT.md` §9) |
| 札を引く | `TakeTray(index)` / `TakeDeck()` | 引く画面で、トレイの札 / 山札をタップ。トレイは確定が要る | 確認済み。**山札は押した時点で確定し、取り消しが消える**。演出の約 5 秒は確定が効かない |
| 足す分を払う | `ConvertExtra(pay)` / 払わない | 枠の右の変換のボタン → 森林: 手札の札を斜線の枠へドラッグ / 草原: 餌をタップ / 湿地: 鳥をタップ(卵)→ 確定 | 確認済み(`RESULT.md` §9) |
| 振り直し | `Reroll()` | 餌箱の残りが同じ目のとき、枠の右の巣箱のボタン(赤い印) | 確認済み(取り消せない) |
| 鳥の能力 | `ChooseOption(option)` | 選択肢(生息地、× / ✓、「蓄える / 取る」)をタップ → 確定。差し込みは手札の札を斜線の枠へドラッグ | 確認済み(`RESULT.md` §9、§10) |
| 鳥の能力 | `SkipPower()` | 右下のスキップ → 確認の「スキップ」(2 操作) | 確認済み |
| 確定 | `Confirm()` | 右下の確定 | 確認済み |
| 取り消し | `Undo()` | 左下の赤い矢印 | 確認済み。**行動を選ぶ前まで戻る**(executor が食い違いを戻すときだけ使う。思考は選ばない) |

- **赤い印の付いた確定と、山札から引く操作は取り消せない**。`Confirm` の前に「画面の状態 = 思考が決めた結果」を照合する(「操作の安全」)
- 2 操作の手(`SkipPower`、`Pay` の変更)は、executor の中で 1 操作ごとに画面を確かめる
- ダイスを 1 個取ると残りのダイスが詰めて並び直す(`RESULT.md` §9)。`TakeDie` の位置は毎回その画面から読む
- 演出の途中の入力は無視される。確定・選択の後は、次の決定の表示が出るまで待ってから送る
- **入力は押下方式(押下 → 0.25 秒 → 解放)を既定にする**。`input tap` が効かない場面があった(`RESULT.md` §11。原因は座標の誤りか演出の途中と見ている)。1 回送って画面が変わらなければ、押下方式で 1 回だけ再送し、それでも変わらなければ止まる
- 画面の座標は原寸(2432x1080)だけを持つ。縮小した画像の座標を使わない(`RESULT.md` §11 の取り違え)
- 吹き出し(「鳥をプレイするには、…」)が出ている間はドラッグが効かない。出ていたら空き地を押して閉じる
- 思考は、行動を選ぶ時点で、その手番の決定の列をまとめて決める(論点 3)。以降の `choose` では、画面から読んだ決定に、決めてある答えを順に返す。画面の決定が予定と違えば、その場で決め直す

### 2. 鳥の能力(180 枚)

札ごとに文が違うので、**種類とパラメータ**で表す。`birds.json` の 1 枚は次の形。

```text
name(札名)、habitats、cost(餌の組。「/」は どれか)、points、nest、egg_limit、wingspan_cm、
power: { timing: none | when_played | when_activated | between_turns,
         kind: "gain_food_supply" など, params: {...}, text: 札の文 }
source: 画像名
```

- 能力の種類は `powers/registry.py` に登録する。最初に実装するのは、数の多い種類から(餌を得る、卵を産む、札を引く、餌を蓄える、札を差し込む、鳥を移す、全員が得る)。種類の一覧は、札の表ができてから数えて決める
- **未対応の種類(`Unmodeled`)** の扱い
  - 模擬: 効果なしとして進める(評価が低めに出るだけで、盤面を誤らない)
  - 実機: 案内が出たら `SkipPower` を返す(スキップは正しい操作で、盤面は次の認識で読み直す)。スキップできない案内は、入力を送らず止まる
  - スキップした札名を記録し、対応の優先を決める材料にする
- 能力の結果は、乱数(山札の一番上、ダイス)に左右されるものが多い。`apply` は乱数を引数で受け、実機では「結果待ち」の印を立てて、次の認識で読んだ値を採る(論点 6)
- 桃色の能力(相手の手番中)が発動して自分へ案内が出るかは未確認(2 局目で桃色のヤマセミを置いたが、相手が湿地の鳥を置かず発動を見ていない)。相手の手番の結果は、手番の開始の前に案内として出る(`RESULT.md` §11)ので、`recognizer` はその案内の文と画面の数の変化を読んで追跡に反映する。桃色の発動が案内として出ることを確かめるまでは、**桃色の鳥を置く手を思考から外す**(未知の案内で止まらないため)

### 3. 思考

乱数と隠れた情報が多く、1 手番の分岐も多い。探索木は作らない。

1. **候補の列挙**: 行動 4 種 × その中の選び方(置く鳥と生息地と払い方、取るダイス、卵の配分、引く札)。能力は「使う / スキップ」を使う側で固定し、選択肢があれば列挙する。数が多い行動(産卵の配分)は、評価の高い鳥に寄せる規則で絞る
2. **評価(`evaluation.py`)**: 行動後の局面の値 = 今の得点(`scoring.py`)+ 資源の見込み(餌・手札・卵の空き × 残りの手番で使える分)+ 行の強さ(列の数と茶色の能力の、残りの起動回数の見込み)+ 目的の順位の見込み + ボーナスカードの見込み。重みは `strategy.toml`
3. **乱数のある候補**(ダイス、山札)は、`belief` から標本を引いて平均する
4. 最初の版は 1 手番先まで。自己対戦が動いてから、軽い方針で数手番先まで模擬する版を足し、勝率で比べて採る

- 残りの手番が少ないラウンド 4 は、資源の見込みの重みを 0 に近づける(点にならない餌と札を取らない)
- 初期選択は、札 5 枚と餌 5 種から 5 つの組(252 通り)を、同じ評価値(1 手番目に置ける鳥があるかを加点)で比べる
- 相手の手番の模擬(`opponents.py`)は、数手番先を読む版を足すときに作る。最初の版は自分の 1 手番の貪欲な先読みで、相手を模擬しない(実装済み: 無作為の方針に 39 勝 1 敗。評価で「手札を一律に高く数える」と、払えない札を溜めて全敗した。手札は「払える割合」と「使い切れる枚数」で数える)
- 持ち時間(初期値): 行動を選ぶとき 10 秒、以降の決定は決めてある答えを返すだけ

### 4. 札名の読み方と、札の表の作り方

**札名は、日本語の認識モデルの OCR で読み、札の表と照合する**(2026-11-13 に試験。`RESULT.md` §6)。

- エンジンは 2 つ持つ: 日本語(`models/ocr/japan_PP-OCRv4_rec_infer.onnx`。札名、案内、能力の文)と、既定(数字。日本語のモデルは翼長の数字を誤る)。数字は桁のテンプレートを先に試し、OCR は確認に使う
- 読んだ名前は、札の表の名前と照合する(編集距離の最も近い 1 つ。2 番目との差が小さければ「読めない」)。シ/ツ、ン/ソ、コ/ユ の取り違えと、2 行に分かれた札名を、ここで吸収する
- **翼長・点・生息地の印で確かめる**(札の表の値と合わなければ「読めない」)
- 読めない札は「不明」として持ち、置く・払うの対象にしない。自分の手札が読めなければ、札をタップして大きくした表示で読み直し、それでも読めなければ止まる
- OCR のエンジンは `plugins/monopoly/vision/ocr_engine.py` にある。プラグインの間で import しないので、`toolkit/ocr_reader.py` へ移し、認識モデルの経路を引数で受ける形にする(Jaipur・Nature の設計と同じ。先に実装した方が移す)。**共通基盤の変更として記録する**
- 採らなかった案: 表示言語を英語に替える(設定の変更が要る)、札の絵のテンプレート(絵を集める元が無い)

**札の表(`birds.json`)は、対局で見えた札を写して増やす**。ルールブックと付録に一覧は無く、メニューの「鳥」は裏向きで使えない(`RESULT.md` §7)。

- 大きい札(初期選択、手札の拡大、引く画面、プレビュー)は全文が出る。`scripts/wingspan/collect_cards.py` が、保存画面から大きい札を切り出し、札名・点・翼長・能力の文を OCR で読んで下書きを作る。**生息地・コスト・巣・卵の上限は印なので、人が画像を見て確かめてから表に入れる**(出典は画像名)
- 対局中に表に無い札名を読んだとき(`UnknownCardError`): 大きい札の画面を保存して記録する。自分の手札なら置かない。相手の盤なら、全体ボードの概要(点、卵の印)だけを読み、能力は「未対応」と同じに扱う。**表に無いことを理由に止めない**(札の表が揃うまで動かなくなるため)。ただし、照合の候補が近くに 2 つあるとき(読み誤りの疑い)は止まる
- 名前のボーナス(色・部位・地名・人名)は英語の札名で決まる(A p.4)。日本語の表示でどの鳥が当たるかは、札の表に持たせず、最初は評価に入れない(ボーナスカードの下に出る現在の数は読む)
### 5. 画面の読み方

**盤面は全体ボードの表示で読む**。配置が固定(3 行 × 5 列)で、鳥・卵・ダイス・トレイが 1 画面に入る(`RESULT.md` §2)。

1. `screens.py`: 画面種別と、表示の種類(生息地 / 全体ボード)、札の表示のタブ(概要 / 能力 / トリビア)を画面から決める。**覚えている値を使わない**(`RESULT.md` §2 の注意)
2. `recognizer` は、盤面を読む前に表示を揃える: 全体ボードでなければ (142,767) を押す、タブが概要でなければ (320,308) を押す。**これらは盤面を変えない入力として、`recognizer` が送ってよい入力の一覧に入れる**(顔の切り替え、プレビュー、目的と得点、その戻るも同じ)。1 回押すごとに画面を確かめる
3. `mat.py`: 格子の枠ごとに、札があるか(枠の色)、札名(`card_reader`)、塗られた卵の数、蓄えた餌(札の右下の丸い札: 餌の印と数)、差し込んだ札(札の右下の四角: 札の印と数)
4. `counters.py`: 右の数字(キューブ、卵、餌)は桁のテンプレート。相手の分は、相手の顔を押して同じ位置で読む
5. `feeder.py`: ダイスの目(果実、魚、虫、ネズミ、種、虫/種)を印のテンプレートで分類する。餌箱の外に出たダイスは数えない
6. `tray.py`: 全体ボードの下の右の 3 枚。山札の残りはプレビューで読む(毎手番は読まない。札を引く候補があるときだけ)
7. `hand.py`: 下の帯。**手札が 4 枚以上のときは、左から重なり、右端の 1 枚だけ全体が見える**(5〜6 枚で確認。`RESULT.md` §11)。重なって名前が隠れる札は、1 枚ずつタップで大きくして読む。ボーナスカードは左端
8. `prompt.py`: 右下の枠の有無、手順のタブ、選択肢の印、確定(印の有無)・スキップ・取り消しの有無
9. **前の状態との照合**: 自分の盤は、追跡している状態(自分の手の結果)と毎回比べる。食い違えば止まる。相手の盤は、毎回読み直した値を採る(差が、相手の 1 手番で起こりうる範囲かを確かめる)

再開のとき(前の状態が無い)は、手番の開始の表示か、行動を選ぶ時点からだけ始められる。盤面・数・トレイ・ダイスは画面から読める。相手の手札の中身と山札の並びは「不明」。

### 6. 予測と実際の盤面の差(`Rules.apply` と `diff`)

- 自分の手のうち、結果が決まるもの(鳥を置く、餌を払う、卵を置く、ダイスを取る)は `apply` で予測し、`diff` で比べる
- 結果が乱数で決まるもの(山札から引く、ダイスの振り直し、捕食)は、`apply` が「結果待ち」の印を立て、次の認識で読んだ値を状態に入れる。`diff` は、読んだ値が起こりうる範囲か(引いた枚数、ダイスの数)だけを確かめる
- 相手の手番は `apply` で予測しない。相手の盤と数の変化が、合法な 1 手番(キューブ −1、4 つの行動のどれか)で説明できるかを確かめる。能力で説明が付かない差は、未対応の能力がある間は警告にとどめ、キューブと盤面の枠の数の食い違いだけを停止の条件にする

### 7. 操作の安全

executor は 1 操作ごとに次の順で動く。

1. 画面種別、自分の手番(顔と手番の表示)、いまの決定(`prompt`)を確かめる。思考の想定と違えば送らない
2. タップ・ドラッグの位置を、固定の領域(`layout.py`)か、その画面の検出結果から決める
3. 入力を 1 つ送る(タップ、またはドラッグ 1.2 秒。値は実測で決める)
4. 画面を取り直し、期待した変化を確かめる
   - 行動の途中: キューブ −1、枠・ダイス・卵の変化、次の決定の表示。**違う結果になっていたら `Undo` を 1 回送って止まる**(行動を選ぶ前まで戻る。`RESULT.md` §7)
   - 確定の後: 変化が無ければ、再実行せずに止まる

- **赤い印の付いた確定の前に、盤面と数が、決めた手番の結果と一致することを照合する**
- ドラッグの経路が、菱形・歯車・左下のボタン・右下の確定の上を通らないことを、送る前に確かめる
- 禁止領域(`layout.py`): メインメニューのストア・オンライン・ニュース・アチーブメント・クレジット・設定・保護区の記録・鳥、起動直後の「ストアに移動」、拡張の画面の鍵つきの内容、歯車のメニューの設定・メインメニュー、ヘルプ。executor がタップを拒否する
- 前面のパッケージが変わった、または未知の画面なら、入力を送らず止まる
- 対局の開始(プレイ → カスタムゲーム → 次へ)と終局後の後始末は、自動の実行ループに入れず、`scripts/wingspan/` の道具に置く。開始の道具は、プレイヤー枠が 人間 1 + AI(強さは設定で指定。既定はイージー)で、拡張が基本 + スウィフトスタート、目的ボードが緑の面であることを確かめてから「次へ」を押す(押すと確認なしで始まる)
- 終局後の後始末は「メニュー」→「ゲームをセーブして保護区の記録をしますか?」で × を押す(保存するかは設定で持ち、既定は保存しない。`RESULT.md` §10)

## コンポーネント設計

### Rules(`logic/rules.py` ほか)
**責務**: 決定ごとの合法手、手の適用、ラウンドの進行と得点、`outcome`(合計点の比較から "win" / "lose" / "draw")、`diff`。
**要点**: 行動は `actions.py`、支払いは `payment.py`、能力は `powers/`、ラウンドは `rounds.py`、得点は `scoring.py` に分ける(1 ファイル 300 行以下)。札の表は `data/*.json` に出典つきで書く。相手の手も同じ `apply` で進められるようにし、模擬で共用する。

### Strategy(`logic/strategy.py`、`evaluation.py`、`belief.py`)
**責務**: 合法手から 1 手を選ぶ。
**要点**: 乱数は `random.Random` を引数で受ける。状態は不変の小さなデータクラスにして `apply` を軽く保つ。合法手が 1 つの決定(`StartTurn`、選択肢の無い `Confirm`)は思考を通さずに返す。

### Recognizer(`vision/recognizer.py`)
**責務**: 画面 → `WingspanState`。相手の進行中は、手番の開始の表示を `toolkit/waiting.poll` で待つ。
**要点**: 送ってよい入力は、盤面を変えないものだけ(論点 5 の 2)。一覧に無い位置へは送らない。

### MoveExecutor(`vision/executor.py`)
**責務**: 手をタップ・ドラッグに変換し、結果を確かめる(上の「操作の安全」)。

## データフロー

```text
1. 画面取得(adb) → 画面種別。対局以外・禁止画面なら停止
2. 相手の進行中なら待つ(手番の開始の表示まで)
3. 行動を選ぶ時点: 表示を全体ボード・概要に揃え、自分と相手の盤、数、ダイス、トレイ、手札を読む
   行動の途中: 案内(決定)と、変化した部分を読む
4. Rules.legal_moves → Strategy.choose(行動を選ぶ時点で手番の予定を決め、以降は予定の答えを返す)
5. MoveExecutor が 1 操作 → 画面の変化で確認(食い違えば取り消して停止) → ログ保存
6. 次の認識で、予測との差を確かめる
7. 終局の画面を検出したら停止(詳細 (1747,985) を開いて項目ごとの数と合計を記録)。後始末の道具が「メニュー」→ 保護区の記録の確認で × を押す
```

## エラーハンドリング戦略

- 新しい例外クラスは作らない。`core/errors.py` の既存の例外と、`Recognition.low_confidence`、`ExecutionResult(success=False, reason=...)` で表す
- 想定外の画面、信頼度不足、禁止画面、合法手が 0、追跡と画面の食い違い、照合の候補が 2 つ近い札名、読めない自分の手札、スキップできない未対応の能力 — いずれも入力を送らず停止する
- 操作後に期待した変化が無ければ、再実行ではなく停止して画面を保存する

## テスト戦略

### ユニットテスト(`tests/plugins/wingspan/unit/`)
- logic: 4 つの行動と列ごとの強さ、卵のコスト、餌の払い方、ラウンドの手番の数、目的の採点、最終の得点。**期待値はルールブックから手で作り、ページを書く**
- logic: 鳥の能力は種類ごとに、札の文から手で作った期待値(札名を書く)。未対応の種類が効果なしで進むこと
- logic: 札の表の検査(札名の重複が無い、生息地・巣・餌の値が定義の範囲、出典があること。鳥の枚数は、揃った時点で 180 を検査に足す)
- logic: 固定シードの自己対戦で完走し、不正な手が出ない。戦略が無作為の方針と規則ベースの方針に勝ち越す
- vision: 合成画像と、記録した実画面(`datasets/eval/wingspan/`)。録画が無い環境は飛ばす
- vision: 札名の照合(近い名前が 2 つあるとき「読めない」になる、翼長が合わないとき「読めない」になる)
- vision: 禁止領域へのタップを executor が拒否する。赤い印の確定を、照合が合わないとき送らない

### 統合テスト(`tests/plugins/wingspan/integration/`)
- 記録画面でのドライラン、リプレイ

### 実機テスト(`tests/plugins/wingspan/device/`)
- 画面取得と疎通(`device` マーカー)

## 実装の順序

1. Phase 0 の続き: カスタムゲームを手で 1 ゲーム終え、`RESULT.md` §4 の残りを埋める。その間の画面から札の表の最初の分を作る
2. 札の表(鳥は見えた分から、ボーナス 26、目的 16)を作り、能力の種類を付録の分類(A p.6〜12)で数える
3. 設計の見直し(本書の「未確認」を埋める)
4. logic(盤・行動・支払い・得点 → 能力を数の多い種類から → 自己対戦 → 戦略)。実機が要らない
5. vision(記録 → テンプレート → 全体ボード → 数・ダイス・トレイ・手札 → 案内 → 評価セット)
6. executor と実機の 1 操作(`scripts/common/step_once.py --game wingspan`)
7. 通しの自動プレイと KPI の測定(2 人、AI)

## セキュリティ考慮事項

- 端末の削除・データ消去の操作はコードに入れない。`adb` は必ず `-s <シリアル>`
- ストア(課金)、オンライン、外部リンクは押さない。鍵つきの拡張はストアへつながると見て押さない
- 繰り返しの自動対局は、記録への影響を確かめてユーザーの確認を得てから行う(`01`「前提・仮定」)
- ゲーム画面、APK、ルールブックの PDF、札の絵のテンプレートをコミットしない

## パフォーマンス考慮事項

- 1 操作の目安は平均 30 秒以内(KPI)。1 手番は 3〜8 操作(行動、選択、能力、確定)の見込み
- 1 ゲームは 26 手番(8 + 7 + 6 + 5。R p.5)。相手の手番は約 5 秒
- OCR は 1 回が重い。盤面の札名は、前の読み取りと枠の絵が変わらなければ読み直さない(枠ごとに絵の差分で判定する)

## 将来の拡張性
