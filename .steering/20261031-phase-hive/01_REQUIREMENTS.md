# 要求内容

## 概要

Android版「Hive」を自動対戦するプラグイン `hive` を追加する。Kahunaと同じ共通基盤(認識→思考→操作のループ、安全装置、ログ、リプレイ、評価)の上に、`plugins/hive/` を書き足す形で作る。

## 背景

- Kahunaの調整が想定より大変だったため、大戦略SSB2(PC、ルールが重い)の優先度を下げ、Androidのボードゲームの自動対戦を増やす方針に切り替える
- 実機(SHG11)にHiveのアプリが導入済みで、Kahunaと同じ接続手段(adb)をそのまま使える
- Hiveは盤が無い(駒が盤を作る)ゲームで、Kahunaの固定盤とは認識と座標の考え方が違う。共通基盤が「固定盤」を前提にしていないかを確かめる題材にもなる(`docs/01` のKPI「共通基盤の変更量」)

## 実装対象の機能

### 1. ルールとシミュレータ(`plugins/hive/logic/`)
- 駒の配置と移動の合法手の列挙、勝敗の判定。画面に依存しない
- アプリが採用する駒の組み合わせ(基本のみか、拡張のモスキート・てんとう虫・ダンゴムシを含むか)を設定で切り替えられる

### 2. 思考(`logic/strategy.py`)
- 持ち時間内で最善手を選ぶ探索(第一案: 評価関数つきの反復深化のアルファベータ)

### 3. 認識(`plugins/hive/vision/`)
- 画面から、盤上の駒(種類、色、積み重なりの段)、手持ちの駒、手番、ダイアログを読む
- 盤の拡大・移動(スクロール)があっても、駒の相対位置からヘックス座標へ変換する

### 4. 操作(`vision/executor.py`)
- 「手持ちの駒/盤上の駒を選ぶ → 置き先を選ぶ」をタップ(またはドラッグ)に変換し、結果を画面で確認する

### 5. 組み込み
- `config/hive.toml`、プラグインの登録、`bglm run/eval/replay --game hive` が動く
- `tests/plugins/hive/`、必要なら `scripts/hive/`、`assets/hive/`、`datasets/{eval,raw}/hive/`

## 受け入れ条件

### Phase 0(実機で確かめる)
- [ ] 端末が接続され、Hiveのパッケージ名とバージョンが記録されている
- [ ] 画面取得と1回のタップが通ることを確かめ、座標系(回転後の座標をそのまま使えるか)が記録されている
- [ ] 対戦相手の種類(CPU戦、ローカル2人、オンライン)と、アカウントに影響する操作の範囲が記録されている
- [ ] 採用ルール(拡張駒の有無、先手の決め方、パスの扱い、勝敗の表示)がアプリ内のルールから書き起こされ、`docs/ideas/Hive_アプリ内ルール.md` にある

### ルールとシミュレータ
- [ ] 全駒の移動と配置の規則を、アプリ内ルールの記述から手で作った期待値で検証している(出典付き。実装から期待値を作らない)
- [ ] 自己対戦で1ゲームを完走し、不正な手が出ない

### 認識・操作
- [ ] 手ラベル付けした30画面以上で、要素単位95%以上(KPI。仮)
- [ ] 想定外の画面、信頼度不足では入力を送らず止まる

### 自動完走
- [ ] CPU戦の1ゲームを人手介入なしで終えられる割合が8割以上、勝率5割以上(KPI。仮)

## 成功指標

- `docs/01` のKPIを、Hiveについても同じ基準で測る
- 共通基盤(`core/`、`application/`、`infrastructure/`、`toolkit/`)の変更行数を数えて記録する。不足を直した分は理由を書く

## 前提・仮定

- 対象は端末SHG11(シリアル `355092380222016`)のHive — 根拠: ご指示(実機にインストール済み)と `CLAUDE.md` の端末
- 接続手段は adb、座標系の扱いはKahunaと同じ — 根拠: `CLAUDE.md`「実機の操作」。端末を変えたら最初の1タップで確かめる
- まず**CPU戦(または相手がアプリ内AI)だけ**を対象にする。オンライン対戦や戦績・課金に関わる操作は、実行前にユーザーへ確認する — 根拠: `CLAUDE.md`「ユーザーのアカウントに影響する操作は事前に確認する」
- 駒は基本の8種+拡張3種のうち、アプリが採用するものだけを実装する。決めるのはPhase 0の後 — 根拠: アプリ未確認
- ルールの正本はアプリ内ルール。外部のルール解説との違いが見つかったらアプリ内を優先し、出典を書く — 根拠: Kahunaでの経験(`docs/01` の前提)
- 大戦略SSB2は凍結する(削除はしない)。`docs/01` 等のSSB2の優先度記述は、Phase 0の完了後にユーザーの承認を得て更新する — 根拠: ご指示(優先度を下げる)と、docs作成時は1ファイルずつ承認を得る原則
- アプリを離れるときはHOMEキーを使い、`am force-stop` は使わない — 根拠: `CLAUDE.md`

## スコープ外

- 大戦略SSB2の作業(凍結)
- 強いAI(エンジン並みの強さ)の追求。まず完走と勝率5割を目標にする。強化は後日
- オンライン対戦、ランク戦、課金要素の操作
- アプリの改造・再署名
