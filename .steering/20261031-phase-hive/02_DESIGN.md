# 設計書

## アーキテクチャ概要

Kahunaと同じ。`GamePlugin` の実装を `plugins/hive/` に足し、共通基盤は触らない。`application` は `PluginRegistry` が設定のゲーム名から動的に読み込む。

```text
plugins/hive/
├── __init__.py        # create_plugin()
├── logic/             # 画面に依存しない
│   ├── models.py      # HexCoord, Piece, Board, HiveState, HiveMove
│   ├── rules.py       # 合法手の列挙、勝敗
│   ├── strategy.py    # 探索と評価関数
│   └── simulation.py  # 自己対戦
├── vision/
│   ├── recognizer.py  # 画面 → HiveState
│   ├── pieces.py      # 駒の種類・色の分類(テンプレート)
│   ├── grid.py        # 画面座標 ↔ ヘックス座標
│   ├── screens.py     # 画面種別(盤、ダイアログ、結果)
│   └── executor.py    # HiveMove → タップ列
└── data/
    └── strategy.toml  # 評価関数の重み
```

## 最初に決める設計上の論点

### 1. 座標系: 盤が無い
Kahunaは固定盤(`board.json`)。Hiveは駒が盤を作るので、`HexCoord(q, r)`(軸座標)で持ち、盤は「駒がある座標の集合」とする。手の比較や保存のため、絶対座標に依存せず、最小の q、r を原点にずらして正規化できるようにする。認識側は、画面上の駒の位置からヘックス座標を復元する(`grid.py`)。

### 2. 積み重ね
カブトムシ(拡張ではモスキート、てんとう虫も)は他の駒の上に乗る。座標ごとに駒のスタック(下から上)を持つ。外から見える駒は一番上。

### 3. 画面の変化
盤の拡大・移動・自動センタリングがあり得る。認識は毎回、画面内の駒の間隔(ヘックスの大きさ)から格子を復元する。駒が1個だけのときは、手持ちの駒と同じ大きさを基準にする。**実機で確かめてから書く**(`CLAUDE.md`: 画面の配置は操作して確かめる)。

### 4. 手の表現
- `Place(piece_kind, to)`: 手持ちから置く
- `Move(frm, to)`: 盤上の駒を動かす
- `Pass`: 動かせる駒が無いときの手番放棄(ルールが認める場合のみ)

### 5. 共通基盤で不足しそうな点(確認項目)
- `Recognition` が固定盤を暗黙に前提していないか
- `Strategy` に渡す持ち時間の単位
- `Rules.legal_moves` の戻り値の大きさ(Hiveは序盤から数十手)
- 不足は「インターフェースの不足」として記録する(`docs/01` のKPI)

## コンポーネント設計

### Rules (`logic/rules.py`)
**責務**: 配置の合法性(自分の駒にだけ隣接、相手の駒に隣接しない、4手番目までにクイーン等)、移動の合法性(ワンハイブ規則、滑り込み規則、各駒の移動)、勝敗(クイーンが6方向を囲まれる)、パス。
**要点**: 駒ごとに関数を分ける。1ファイル300行を超えたら分割(`docs/04`)。拡張駒は設定のフラグで有効化。細則はアプリ内ルールを正本とする。

### Strategy (`logic/strategy.py`)
**責務**: 合法手から1手を選ぶ。
**要点**: 反復深化+アルファベータ+手の並べ替え。評価関数の候補: 相手クイーンの周りの埋まり数、自分のクイーンの周りの埋まり数、動かせる駒の数(機動力)、ピン留めされた駒。重みは `data/strategy.toml`。乱数は `random.Random` を引数で受ける(ruffで強制)。

### Recognizer (`vision/recognizer.py`)
**責務**: 画面 → `HiveState` と `UiState`。信頼度が足りなければ入力を送らず止まる。
**要点**: 駒の種類・色はテンプレートマッチングで読む(VLMは切り出した1要素の分類に限る。`CLAUDE.md`)。積み重ねの段数が数えにくい場合、アプリの表示を実機で確かめる。

### MoveExecutor (`vision/executor.py`)
**責務**: `HiveMove` をタップ列に変換し、実行後に画面の変化で結果を確認する。
**要点**: 「駒を選ぶ→置き先候補の強調表示→置き先をタップ」か、ドラッグかは**Phase 0で実機で確かめる**。

## データフロー

```text
1. 画面取得(adb) → Recognizer が HiveState を作る(信頼度不足なら停止)
2. 手番が自分でなければ待つ
3. Rules.legal_moves → Strategy.choose(持ち時間)
4. MoveExecutor が操作 → ChangeDetector で結果確認 → ログ保存
5. 終局の画面を検出したら停止
```

## エラーハンドリング戦略

- 想定外の画面、信頼度不足、合法手が0(パスが無い場合)は入力を送らず停止する。読み取りの失敗を既定値で埋めない
- 認識した盤面から合法手が1つも作れない場合は、認識の誤りを疑って停止する
- 操作後に期待した変化が無ければ、再実行ではなく停止して画面を保存する

## テスト戦略

### ユニットテスト(`tests/plugins/hive/unit/`)
- logic: 駒ごとの移動、ワンハイブ、滑り込み、配置、勝敗、パス。**期待値はアプリ内ルールから手で作り、出典を書く**
- logic: 自己対戦で完走し、不正な手が出ない(固定シード)
- vision: 合成画像と、記録した実画面(`datasets/eval/hive/`)。録画が無い環境は飛ばす

### 統合テスト(`tests/plugins/hive/integration/`)
- 記録画面でのドライラン、リプレイ

### 実機テスト(`tests/plugins/hive/device/`)
- 画面取得と疎通(`device` マーカー)

## 依存ライブラリ

追加なし(`numpy`、`opencv-python`、`pillow`)。

## 実装の順序

1. Phase 0: 実機の疎通と素材の確認(ここで素材が揃わなければ中止判断)
2. ルールの書き起こし(アプリ内ルール)とdocsの追記
3. logic(ルール→自己対戦→戦略)
4. vision(記録→テンプレート→認識→評価セット)
5. executor と実機の1手
6. 通しのCPU戦

## セキュリティ考慮事項

- 端末の削除・データ消去の操作はコードに入れない。`adb` は必ず `-s <シリアル>`
- 対戦の開始、戦績が変わる操作は事前にユーザーへ確認する
- ゲーム画面やAPKをコミットしない(`assets/`、`datasets/`、`runs/`、`apk/` はGit管理外)

## パフォーマンス考慮事項

- 1手の目安は平均30秒以内(KPI)。探索の持ち時間は設定で持つ

## 将来の拡張性

- 強化: 評価関数の調整、自己対戦での重みの探索
- 拡張駒の追加は設定のフラグと駒ごとの移動関数の追加だけで済む構造にする
