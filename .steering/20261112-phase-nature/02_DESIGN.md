# 設計書

> 事実の正本は `RESULT.md`(実機とルール)。本書は「何をどの部品に持たせるか」を決める。確かめていないものは「未確認」と明記し、Phase 0 の続きで埋める。Go / No-Go は 2026-11-12 に Go と判断した(`RESULT.md` §7)。

## アーキテクチャ概要

Kahuna・Hive と同じ。`GamePlugin` の実装を `plugins/nature/` に足す。共通基盤の変更は 1 点を見込む(押下・移動・解放を分けて送る入力。「操作の安全」)。`application` は `PluginRegistry` が設定のゲーム名から動的に読み込む。

```text
plugins/nature/
├── __init__.py          # create_plugin()。組み立てと公開だけ
├── logic/               # 画面に依存しない
│   ├── models.py        # Trait、Card、Species、PlayerState、NatureState、Phase、手(下の表)
│   ├── cards.py         # 札の定義(形質 8 種とハンター。食料の値、狩り・防御の値)。data/cards.json を読む
│   ├── adapting.py      # 適応フェイズの合法手と適用(形質、個体数、大きさ、ハンター、外す、手番を終える)
│   ├── feeding.py       # 給餌フェイズの合法手と適用(採食、狩り、植物を足す、餓死、パス)
│   ├── traits.py        # 形質の効果(食べる量、狩りと防御の値、きっかけで起きる効果)
│   ├── rounds.py        # 準備(新しい種、引き継ぎ、配り)、形質の公開、得点、ユキヒョウの移動、終了
│   ├── rules.py         # Rules(legal_moves / apply / is_terminal / outcome / diff)
│   ├── belief.py        # 隠れた情報の標本化(相手の手札、裏向きの形質、山札)
│   ├── opponents.py     # 相手の方針の模型(模擬と自己対戦で使う)
│   ├── evaluation.py    # 局面の評価値
│   ├── planner.py       # 適応フェイズの案(札の使い方の組)の列挙と絞り込み
│   ├── strategy.py      # 手の選択(案 × 無作為化した試行)
│   └── simulation.py    # 自己対戦(1 ゲーム完走)
├── vision/
│   ├── layout.py        # 固定の領域(下のバー、メニュー、ラウンド、得点の袋、上の札)、禁止領域
│   ├── screens.py       # 画面種別とフェイズ
│   ├── boards.py        # 種のボードの検出(緑と青の珠の組)と、ボードごとの座標系
│   ├── species_reader.py # 1 つのボード: 個体数、大きさ、形質の枠、空腹・満腹の点、ハンター、持ち主
│   ├── digits.py        # 珠・葉・袋の数字
│   ├── watering_hole.py # 水場の位置と個数
│   ├── hand.py          # 手札の枚数、札ごとの位置、札の種類(絵)、食料の値
│   ├── card_zoom.py     # 札を長押しして拡大表示の札名を読む(絵で決まらないときの確認)
│   ├── prompt.py        # 下のバーの案内文(自分の手番、給餌の催促、名前)
│   ├── recognizer.py    # 前の状態と照合して NatureState にする
│   └── executor.py      # 手 → ドラッグ / 押下、結果の確認
└── data/
    ├── cards.json       # 札の内訳(出典つき)
    ├── strategy.toml    # 評価の重み、試行回数、案の数の上限
    └── templates/       # 画面判別、数字、札の絵
```

## 最初に決める設計上の論点

### 1. 手の単位: 1 操作 = 1 手

| フェイズ | 手 | 操作 | 確認 |
|---|---|---|---|
| 適応 | `PlayTrait(card, species)` | 手札 → 形質の枠へドラッグ | 確認済み |
| 適応 | `GrowPopulation(card, species)` | 手札 → 緑の珠へドラッグ | 確認済み |
| 適応 | `GrowSize(card, species)` | 手札 → 青の珠へドラッグ | 確認済み |
| 適応 | `BecomeHunter(species)` | ハンターの山 → 形質の枠へドラッグ | 確認済み |
| 適応 | `RemoveTrait(species, slot)` | 未確認 | 未確認 |
| 適応 | `Undo()` | 取り消しをタップ | 確認済み(executor が食い違いを戻すときだけ使う。思考は選ばない) |
| 適応 | `EndTurn()` | End Turn を押下 0.25 秒 | 確認済み |
| 給餌 | `Forage(species)` | 種 → 水場へドラッグ | 確認済み |
| 給餌 | `Hunt(species, prey)` | 種 → 獲物のボードへドラッグ。**押したまま獲物の上で止め、白い縁取りが意図した獲物に出ていることを確かめてから離す** | 確認済み(`RESULT.md` §6) |
| 給餌 | `AddPlants(card)` | 未確認 | 未確認 |
| 表示 | `Acknowledge(kind)` | ラウンドの切り替わりなどを閉じる | 未確認 |

- 適応フェイズは、End Turn を送るまで盤面が確定しない。`EndTurn` だけが取り消せない操作で、送る前に「画面の種の状態 = 思考が決めた案の結果」を照合する
- 餓死はアプリが自動で進める(確認済み)ので、手にしない。パスも自動と見ている(未確認)
- 空腹のハンターは、狩れる相手がいれば必ず狩る(ルール p.16)。合法手は「狩りの値 ≥ 防御の値」で作り、画面の珠の値(赤 = 狩り、灰色 = 防御)と照合する
- 狩られる個体を選ぶ場面(獲物の持ち主が選ぶ)があるかは未確認。あれば手を足す

### 2. 隠れた情報

| 分からないもの | 扱い |
|---|---|
| 相手の手札 | 枚数だけ持つ(画面で見えるかは未確認。見えなければ「前の残り + 5 − 使った数」で数える)。中身は、札の内訳から、見えた札(自分の手札、表の形質、捨てられた札)を引いた残りから無作為 |
| 相手の裏向きの形質 | 「不明の形質」として枠に持つ。公開で確定する。アプリで自分の手番の時点に相手の形質が見えるかは未確認 |
| 山札 | 残りの多重集合から無作為 |
| 相手の得点 | 食べた数を観測して積む。画面に出るかは未確認 |
| 読めなかった札 | 「不明」として持つ(推測で埋めない)。自分の手札が読めないときは、長押しの拡大表示で確かめ、それでも読めなければ止まる |

### 3. 思考

適応フェイズは「札 n 枚の使い方」の組み合わせが多く、給餌フェイズは相手の出方で結果が大きく変わる(ラウンド 1 で、相手のハンターに 2 回狩られて絶滅した。`RESULT.md` §2)。

1. **案の列挙(`planner.py`)**: 手札の各札を {形質(どの種)、個体数、大きさ、温存} に割り当てる案と、ハンターになるかを列挙する。同じ種類の札は区別しない。数が多いときは、軽い評価で上位(初期値 30 案)に絞る
2. **試行**: 案ごとに `belief` から標本(相手の手札と、相手の適応の結果)を引き、給餌フェイズを `opponents.py` の方針(相手)と軽い方針(自分)で最後まで模擬する
3. **評価(`evaluation.py`)**: ラウンド末の「自分の得点 − 相手の最大の得点」に、次のラウンドへの持ち越し(生き残った種、残した手札、失った個体数の引き継ぎ)を足す。最終ラウンドは順位そのもの。重みは `strategy.toml`
4. 平均の最も高い案を採り、**案の先頭の 1 手を返す**。次の `choose` では、画面から読んだ状態で残りの案を作り直す(状態が同じなら同じ案に落ち着くよう、乱数の種を手番ごとに固定する)

- 給餌フェイズも同じ仕組みで、候補の行動ごとに残りの給餌を模擬して選ぶ
- 守りを評価に入れる: 相手がハンターになる標本で、自分の種の防御の値(大きさ + 形質)が足りない案は、絶滅の損(得点と形質の損失)が出る
- `opponents.py` の最初の版は規則ベース(ハンターになって狩れる相手を狩る、狩れなければ採食)。EASY AI の観測で直す
- 探索木は作らない(Colt Express と同じ方針)

### 4. 予測と実際の盤面の差(`Rules.apply` と `diff`)

- 自分の適応の手は確定的(手札が 1 枚減り、種の値が変わる)。`diff` は自分の種と手札の枚数を比べる
- `EndTurn` の後(相手の適応、形質の公開)と、給餌フェイズの相手の行動は、`apply` で予測しない。「相手の進行を待つ」印を立て、`diff` はその間の変化を数えない
- 代わりに `recognizer` が、**観測した変化を合法な進行で説明できるか**を確かめる(水場の減り = 採食の量、自分の個体数の減り = 狩りまたは餓死、相手の赤い点の増え = 肉の量)。説明できなければ止まる
- 自分の `Forage` は、食べる量がルールで決まる(大きさ + 形質、水場と空腹の数が上限)ので、`diff` で水場の減りと満腹の点を比べる

### 5. 画面の読み方(フェイズで倍率と位置が変わる)

固定の座標で種を読まない。**ボードを見つけてから、ボードの中の相対位置で読む**。

1. `screens.py`: 下のバー(固定の位置)の形と文で、適応(End Turn と取り消しがある)か給餌(案内か名前)かを決める
2. `boards.py`: 緑の珠と、その右の珠(青・赤・灰色)を色の連結成分で探し、左右に並ぶ組を 1 つのボードとする。珠の間隔からボードの倍率を出し、形質の枠 3 つ・中央の印・下の点の位置を決める。試作(`scripts/nature/probe_boards.py`)は 25 画面中 21 画面で数が一致した。外したのは、満腹の印が珠に接した画面と演出の途中のコマ(`RESULT.md` §7)。個体数の珠は、右の珠からの相対位置でも読めるようにし、同じ読み取りが 2 回続くまで待つ
3. 持ち主: 中央の印(自分 = 羊、相手 = 別の絵)と、画面の上下で決める。2 人戦では上 = 相手、下 = 自分(複数の種のときの並びは未確認)
4. `species_reader.py`: 珠の数字、枠の札(空 / 裏 / 札の種類)、点の色(茶 = 空腹、緑 = 植物、赤 = 肉。緑は未確認)、ボードのとげ(ハンター)
5. 水場: 葉の上の数字を読む(植物の駒は数えない)
6. 手札: 下の帯で札の左上の葉(食料の値)を探して枚数と位置を出し、札の絵をテンプレートで分類する。重なって絵が見えない札(9 枚のとき左が重なる)は、追跡(前の手札 + 引いた枚数)と葉の数で枚数を合わせ、種類が決まらなければ長押しの拡大表示で読む
7. **追跡との照合**: 種の数、個体数、大きさ、形質は、論理側で追っている状態と毎回比べる。食い違えば止まる

再開のとき(前の状態が無い)は、適応フェイズの自分の手番からだけ始められる。相手の手札の枚数と山札は「不明」から始め、札の内訳から見えている札を引く。

### 6. 認識の手段

- 画面種別: 固定位置のテンプレート(メニューの題字、LAUNCH GAME、読み込み、End Turn、設定の題字、ラウンドの表示)
- 数字: 桁のテンプレート(珠の白い数字、葉の緑の数字、袋の数字)。倍率が 2 通り以上あるので、ボードの倍率に合わせて拡大縮小してから比べる
- 札の種類: 絵のテンプレート(9 種)。拡大表示の札名は OCR(RapidOCR)で読む。エンジンの共有は Jaipur の設計(`toolkit/ocr_reader.py` へ移す)と同じで、先に実装した方が移す
- 案内文: 下のバーの文をテンプレートで判別する(「Your turn! Play your Trait cards.」「FEED YOUR SPECIES」、名前の表示)
- 3D の描画で、同じ場面でも光り方(手番の種が光る、札が光る)が変わる。色の判定は珠の中心など光の影響が小さい所で行い、閾値は評価セットで決める
- VLM は使わない

### 7. 操作の安全

executor は 1 手ごとに次の順で動く。

1. 画面種別とフェイズ、自分の手番(案内文)を確かめる。違えば送らない
2. 始点(札の位置、種の中央)と終点(枠、珠、水場、獲物)を、**その画面の検出結果から**決める
3. 入力を 1 つ送る(ドラッグ 1.5 秒、押下 0.25 秒。値は実測で決める)
4. 画面を取り直し、期待した変化を確かめる
   - 適応: 手札が 1 枚減り、対象の値が変わる。**違う結果になっていたら `Undo` を 1 回送って止まる**(違う枠・珠に入った場合に、盤面を戻してから人に渡す)
   - 給餌・End Turn: 変化が無ければ、再実行せずに止まる

- `EndTurn` の前に、種の状態が案の結果と一致することを照合する(論点 1)
- ドラッグの経路が、メニュー・チャット・取り消し・End Turn の上を通らないことを、送る前に確かめる
- 押下は「押下 → 待機 → 解放」で送る。共通の `HoldDrag`(始点 = 終点)で表せる見込みで、実装前に確かめる
- **狩りは「押下 → 移動 → 撮影 → 解放」に分けて送る**(実機で成立を確認。`RESULT.md` §6)。共通の入力は 1 つの動作を最後まで送る形(`Tap`・`Drag`・`HoldDrag`)なので、押下・移動・解放を別々に送る入力を `core` と `infrastructure/adb_device.py` に足す必要がある。**共通基盤の変更(インターフェースの不足)として記録する**
- 右の珠は、大きさ(青)・狩りの値(赤)・防御の値(灰色)を切り替えて表示する。読むときは色で種類を決め、大きさとして扱ってよいのは青のときだけ。大きさは追跡の値と照合する
- 禁止領域(`layout.py`): メニューの ONLINE GAME・TODAY'S DUEL・CAMPAIGN・右のタブ(HOME 以外)、LOCAL GAME のモジュールと HUMANS、対局中のチャット、設定の MAIN MENU・QUIT・REPORT A BUG と設定値の矢印。executor がタップを拒否する
- 前面のパッケージが変わった、または未知の画面なら、入力を送らず止まる
- 対局の開始(LOCAL GAME → EASY AI → LAUNCH GAME)と終局後の後始末は、自動の実行ループに入れず、`scripts/nature/` の道具に置く。開始の道具は、モジュールが選ばれていないことを確かめてから LAUNCH GAME を押す

## コンポーネント設計

### Rules(`logic/rules.py` ほか)
**責務**: フェイズごとの合法手、手の適用、準備と得点、`outcome`(自分の順位から "win" / "lose" / "draw")、`diff`。
**要点**: 適応は `adapting.py`、給餌は `feeding.py`、形質は `traits.py`、ラウンドの進行は `rounds.py` に分ける(1 ファイル 300 行以下)。札の内訳は `data/cards.json` に出典(ルールブックのページ、または実機の画像名)つきで書く。相手の手も同じ `apply` で進められるようにし、模擬と追跡で共用する。

### Strategy(`logic/strategy.py`、`planner.py`、`evaluation.py`、`belief.py`、`opponents.py`)
**責務**: 合法手から 1 手を選ぶ。
**要点**: 持ち時間の中で試行回数を決める。乱数は `random.Random` を引数で受ける。状態は不変の小さなデータクラスにして `apply` を軽く保つ。`Acknowledge` しか無い場面は思考を通さずに返す。

### Recognizer(`vision/recognizer.py`)
**責務**: 画面 → `NatureState`。相手の進行中は落ち着き(自分の手番の案内)を `toolkit/waiting.poll` で待ち、その間の変化(水場、個体数、点)を集めて、合法な進行で説明する。
**要点**: 送ってよい入力は、札の長押し(拡大表示)だけ。盤面を変えない操作であることは確認済み(`RESULT.md` §2)。

### MoveExecutor(`vision/executor.py`)
**責務**: 手をドラッグ・押下に変換し、結果を確かめる(上の「操作の安全」)。

## データフロー

```text
1. 画面取得(adb) → 画面種別とフェイズ。対局以外・禁止画面なら停止
2. 相手の進行中なら待つ(変化を集め、追跡を進める)
3. ボードを検出し、種・水場・手札・ラウンド・得点を読み、追跡と照合して NatureState を作る
4. Rules.legal_moves → Strategy.choose(持ち時間)
5. MoveExecutor が 1 操作 → 画面の変化で確認(適応で食い違えば取り消して停止) → ログ保存
6. 次の認識で、予測との差を確かめる
7. 終局の画面を検出したら停止(順位と得点を記録)
```

## エラーハンドリング戦略

- 新しい例外クラスは作らない。`core/errors.py` の既存の例外と、`Recognition.low_confidence`、`ExecutionResult(success=False, reason=...)` で表す
- 想定外の画面、信頼度不足、禁止画面、合法手が 0、追跡と画面の食い違い(種の数、個体数、大きさ、形質、手札の枚数)、説明できない変化、読めない札 — いずれも入力を送らず停止する
- 操作後に期待した変化が無ければ、再実行ではなく停止して画面を保存する

## テスト戦略

### ユニットテスト(`tests/plugins/nature/unit/`)
- logic: 適応の行動と上限(形質 3 枚、大きさ 4)、採食の量、狩りの成否と結果、形質 8 種とハンター、餓死、絶滅と引き継ぎ、得点。**期待値はルールブックから手で作り、ページを書く**
- logic: `belief` の標本が制約(札の内訳、見えた札)を満たすこと、`planner` が合法な案だけを出すこと
- logic: 固定シードの自己対戦で完走し、不正な手が出ない。戦略が無作為の方針と規則ベースの方針に勝ち越す
- vision: 合成画像と、記録した実画面(`datasets/eval/nature/`。適応と給餌の両方の倍率)。録画が無い環境は飛ばす
- vision: 禁止領域へのタップと、禁止のボタンの上を通るドラッグを executor が拒否する。適応で食い違ったとき取り消しを 1 回だけ送る

### 統合テスト(`tests/plugins/nature/integration/`)
- 記録画面でのドライラン、リプレイ

### 実機テスト(`tests/plugins/nature/device/`)
- 画面取得と疎通(`device` マーカー)

## 実装の順序

1. Phase 0 の続き: ルールブックを読む。LOCAL GAME を手で 1 ゲーム終え、`RESULT.md` §4 を埋める(ボードの検出と狩りの操作が決まらなければ中止判断)
2. 設計の見直し(本書の「未確認」を埋める)
3. logic(札の表 → 適応・給餌・形質 → 自己対戦 → 戦略)。実機が要らないので、1 のルールブックの後は並行できる
4. vision(記録 → テンプレート → ボードの検出 → 種・水場・手札の読み取り → 評価セット)
5. executor と実機の 1 手(`scripts/common/step_once.py --game nature`)
6. 通しの自動プレイと KPI の測定(2 人、EASY AI)

## セキュリティ考慮事項

- 端末の削除・データ消去の操作はコードに入れない。`adb` は必ず `-s <シリアル>`
- ログイン済みのアカウントで動く。ONLINE GAME、TODAY'S DUEL、STORE、ACCOUNT、FRIENDS、チャット、外部リンクは押さない
- 繰り返しの自動対局は、記録への影響を確かめてユーザーの確認を得てから行う(`01`「前提・仮定」)
- ゲーム画面、APK、ルールブックの PDF をコミットしない。ログと記録に、アカウントのメールアドレスが映る画面(ACCOUNT)を含めない

## パフォーマンス考慮事項

- 1 手(1 操作)の目安は平均 30 秒以内(KPI)。ドラッグ 1.5 秒 + 演出 + 画面取得 2 回で、操作そのものは 5 秒前後の見込み
- 1 ゲームは 4 ラウンド。自分の操作は、適応が 1 ラウンド 5〜10 回、給餌が種の数 × 数回
- 思考の持ち時間(初期値): 適応の最初の 1 手 10 秒(案の評価をまとめて行う)、以降と給餌は 3 秒
