## プロダクト概要

### 名称
**BoardGameLLM** - ローカルPCで複数のターン制ボードゲームを自動プレイする、プラグイン式ゲームエージェント

### プロダクトコンセプト
- **共通基盤+ゲーム別プラグイン**: 画面取得・操作・実行ループ・ログ・ローカルVLMは全ゲーム共通。盤面認識・ルール・思考ロジックはゲームごとのプラグインとして分離する
- **VLMは認識の補助、思考は自作ロジック**: 4GB VRAMの小型VLMに「最善手の探索」は任せない。盤面を構造化データへ変換し、合法手の列挙と手の選択はルール実装+探索アルゴリズムが担う
- **軽い手段から段階的に**: 盤面認識は OpenCV → 小型CNN/OCR → ゼロショットVLM → LoRA付きVLM の順に、足りない場合だけ重い手段へ進む。LoRA学習が必要な場合のみ Kaggle / Google Colab のGPUを使い、完成物は手元の4GB環境で動かす

### プロダクトビジョン
ボードゲームのターン制戦略ゲームを、人が見守るだけで1ゲーム分自動で遊べる状態にする。
最初の2タイトル(ルールが単純なAndroid版Kahuna、次にAndroid版Hive)で共通基盤を磨き、3本目以降は「認識・ルール・AI」のプラグインを足すだけで対応できる構造を目指す。大戦略SSB2は、Kahunaでの調整の負担を受けて優先度を下げ、Androidゲームの追加を先に進める方針に変えた(再開は別途判断する)。
高価なGPUを持たない個人PC(VRAM 4GB)で実用になることを前提とし、学習が必要な部分だけクラウドの無料GPU環境に逃がす。

### 目的
- 4GB VRAMのローカルPCで、ターン制ボードゲームを1ゲーム通して自動プレイできるようにする(Kahuna、Hiveを優先。大戦略SSB2は凍結)
- 新しいゲームの追加を「共通基盤は触らずプラグインを書く」作業に閉じ込める
- 盤面認識の精度と、思考ロジックの強さを別々に評価・改善できる仕組みを持つ

## 解決したい課題

| 課題 | 現状 | 本プロダクトによる解決 |
|---|---|---|
| ターン制ゲームの周回・反復プレイを手動で行う負担 | 人が1手ずつ操作 | 認識→思考→操作を自動ループ化 |
| 既存のゲーム用AIエンジンが使えない | 大戦略SSB2に対応エンジンが無く、Kahunaも既存エンジンを前提にできない | ルールシミュレータと探索AIを自作しプラグイン化 |
| 大規模VLMはVRAM 4GBで動かない | 汎用エージェントは大規模モデルの領域 | VLMの役割を認識補助に絞り、小型モデル(Qwen3-VL-2B/4B 4bit等)と古典的画像処理を併用 |
| ゲームごとにLLMを作ると管理が破綻する | ストレージ・学習コストが増大 | ベースモデル1つ+必要なゲームだけLoRA。ルール・認識はプラグイン |

## ターゲットユーザー

### プライマリーペルソナ: 開発者本人(個人開発者・ゲーム愛好家)
- Windows PC を使用。GPUは VRAM 4GB(学習用の大容量GPUは持たない)
- 対象は、Android端末をPC上に表示して遊ぶ「Kahuna」「Hive」と、PCソフト「大戦略SSB2」(優先度を下げて凍結中)
- Pythonで普通にプログラミングできる
- 現在の課題: ターン制ゲームの反復操作に時間を取られる。既存のAIも自動化ツールも無い
- 期待する解決策: 起動して見守るだけで1ゲーム進む。誤認識・停止時は原因が画像とログで追える
- 典型的なワークフロー: ゲームを起動 → ウィンドウ/端末を指定してエージェント起動 → 1手ずつ確認しながら実行 → 慣れたら全自動 → 失敗した画面を保存して認識を改善

## 成功指標(KPI)

### プライマリーKPI
- 盤面認識の正答率: 手ラベル付けした各ゲーム30画面以上で **要素単位 95%以上(仮)**(Kahuna: Phase 1、大戦略SSB2: Phase 2 の完了時)
- 自動完走率: 各ゲームのシングルプレイ(CPU戦。大戦略SSB2は通常マップのうち最も低難度の2勢力マップ「ハロー・大戦略」)1ゲームを人手介入なしで終えられる割合 **8割以上(仮)**(Kahuna: Phase 1、大戦略SSB2: Phase 4 の完了時)
- 新規ゲーム追加の共通基盤変更量: 3本目のゲーム追加時に共通基盤コードの変更が **0行(インターフェース不足による修正を除く)**(拡張検証時)

### セカンダリーKPI
- 1手あたりの所要時間(認識〜操作完了): ターン制で許容できる **平均30秒以内(仮)**。ただし大戦略SSB2は1ユニットの行動を1手とし、**最大50ユニットの1ターンで10分以内(仮)**
- 思考ロジックの強さ: 対CPU戦(Kahunaは標準難易度、大戦略SSB2は完走率と同じ条件)での勝率 **5割以上(仮)**(Kahuna: Phase 1、大戦略SSB2: Phase 4 の完了時)
- 誤操作率: 実行した操作のうち、画面変化の確認で「意図と異なる」と判定された割合 **2%以下(仮)**

## 機能要件

### コア機能(MVP)

#### F1. 画面取得・操作(共通基盤)

**ユーザーストーリー**:
開発者として、ゲームの種類を問わず同じ方法で画面を読み取り操作したいので、取得と入力を抽象化した層が欲しい

**受け入れ条件**:
- [ ] PC: 指定ウィンドウのスクリーンショットを取得し、ウィンドウ相対座標でクリックできる(大戦略SSB2で確認。キャプチャ・入力が通らない場合の代替手段を検証結果として記録する)
- [ ] Android: `adb` で画面取得と tap 操作ができる(ミラー表示は人間の確認用で、操作対象にしない)
- [ ] 取得・操作は共通インターフェースの背後に置かれ、プラグインはPC/Androidの差を意識しない
- [ ] 操作後に画面変化の有無を検出できる

**優先度**: P0(必須)

#### F2. 盤面認識

**ユーザーストーリー**:
開発者として、スクリーンショットから盤面を構造化データ(マスの地形・ユニット・所属・HP等)に変換したいので、ゲームごとの認識モジュールが欲しい

**受け入れ条件**:
- [ ] 画面座標と盤面座標(Kahuna: 島と島を結ぶ点線の位置、大戦略SSB2: ヘクス)の相互変換ができる(キャリブレーション手順を含む)
- [ ] Kahunaの杖コマ(細い棒)・カード・カフナコマを読み取れる。認識はAndroid画面の解像度を基準とし、PC上の表示サイズに影響されない
- [ ] 大戦略SSB2は64×64ヘックスのマップ全体を、スクロールを含めて1つの盤面として再構成できる。カメラの拡大率と角度は固定して扱う
- [ ] 大戦略SSB2の索敵範囲外のヘックスを「不明」として区別できる
- [ ] 大戦略SSB2の自勢力部隊の状態は、マップより読みやすければ部隊一覧画面から取得できる
- [ ] 認識結果を元画像に重ね描きしたデバッグ画像を出力できる
- [ ] 認識手段(テンプレートマッチング / 小型CNN / OCR / VLM)をモジュールごとに差し替えられる
- [ ] 手ラベル付けした評価画像セットに対し、正答率を自動計測できる
- [ ] ダイアログ・メニュー等のUI状態を判別し、想定外画面を検出できる

**優先度**: P0(必須)

#### F3. ルール実装と合法手列挙

**ユーザーストーリー**:
開発者として、盤面データから合法手を列挙したいので、ゲームごとのルールシミュレータが欲しい

**受け入れ条件**:
- [ ] 盤面状態から1ターン分の合法手を列挙できる(移動・攻撃・生産・占領など、各ゲームで定義した範囲)
- [ ] 大戦略SSB2のルール(地形防御・拠点・生産・占領・補給・支配エリアなど)はルールブックPDFを入力として実装し、実装した各ルールからルールブックの該当箇所(ページまたは節)を辿れる
- [ ] ルールブックに無い兵器性能と移動力消費は、ゲーム内の兵器詳細画面から収集する
- [ ] ルールブックに無いダメージ計算は、ゲーム内の戦果予測画面の表示で代替する
- [ ] ルールブックと実機の挙動が異なる場合は実機を正として実装し、差異を記録する
- [ ] 実プレイの記録とシミュレータの挙動を突き合わせ、差異をログに出せる(Kahunaはルールページとアプリの差異を観察で補う)

**優先度**: P0(必須)

#### F4. 思考ロジック(AI)

**ユーザーストーリー**:
開発者として、合法手の中から良い手を選んでほしいので、評価関数ベースのAIが欲しい

**受け入れ条件**:
- [ ] 評価関数+貪欲法で1手を選べる(目標への前進、有利な交換比の攻撃、資金に応じた生産など)
- [ ] 思考ロジックは盤面データのみを入力とし、画面・VLMに依存しない(単体でテスト・対戦シミュレーションができる)
- [ ] 思考時間の上限を設定でき、上限に達したらその時点で最善の手を返す
- [ ] 大戦略SSB2はターン全体の組み合わせを探索せず、1ユニットずつ判断する
- [ ] 大戦略SSB2は索敵範囲外の敵部隊が見えない状態でも手を選べる

**優先度**: P0(必須)

#### F5. 実行ループと安全装置

**ユーザーストーリー**:
開発者として、自動プレイを安心して任せたいので、止まる・戻る・止められる仕組みが欲しい

**受け入れ条件**:
- [ ] 取得→認識→思考→操作→画面変化確認 のループを1手ずつ/連続の両モードで実行できる
- [ ] ステップ上限、画面変化なしの検出、緊急停止キーを備える
- [ ] 想定外画面・認識失敗時は操作せずに停止し、原因画像を保存する
- [ ] 遭遇戦などで行動が計画どおりに終わらなかった場合は、盤面を読み直して判断をやり直す
- [ ] オンライン対戦モードでは起動しない(シングルプレイ/CPU戦のみ。利用規約遵守)

**優先度**: P0(必須)

#### F6. ログ・失敗リプレイ

**ユーザーストーリー**:
開発者として、失敗の原因を後から追いたいので、各手の入出力を記録・再生したい

**受け入れ条件**:
- [ ] 各手について スクショ・認識結果・合法手・選択手・操作 を保存する
- [ ] 誤認識した画面を評価セットへ追加できる
- [ ] 保存済みログから認識〜思考を再実行できる(ゲーム画面なしで再現)

**優先度**: P0(必須)

#### F7. ゲームプラグイン機構

**ユーザーストーリー**:
開発者として、新しいゲームを追加するときに共通基盤を触りたくないので、プラグイン境界が欲しい

**受け入れ条件**:
- [ ] プラグインは 認識・ルール・AI・(任意)LoRA/プロンプト設定 をまとめて提供する
- [ ] Kahunaと大戦略SSB2の2本が同一インターフェースで動く
- [ ] プラグインは設定で切り替えられる

**優先度**: P0(必須)

### 拡張機能

#### F8. ローカルVLM連携(認識補助・想定外画面判断)

**ユーザーストーリー**:
開発者として、古典的画像処理で読めない箇所と想定外ダイアログをVLMで補いたいので、ローカルVLMを呼べる仕組みが欲しい

**受け入れ条件**:
- [ ] OpenAI互換API(Ollama / llama.cpp / LM Studio等)経由でVLMを呼べ、サーバを差し替えられる
- [ ] 4GB VRAMで Qwen3-VL-2B(4bit)が動作し、4Bは画像縮小・短コンテキストで動作可否を実測して記録する
- [ ] VLMの出力は検証可能な構造化形式(JSON等)に限定する

**優先度**: P1(重要)

#### F9. 学習データ作成とLoRA学習(Kaggle / Google Colab)

**ユーザーストーリー**:
開発者として、認識精度が足りないゲームだけVLMを強化したいので、データ作成とクラウドGPUでの学習手順が欲しい

**受け入れ条件**:
- [ ] F6のログと自動生成した盤面画像から `(画像, 正解配置)` のデータセットを作れる
- [ ] Kaggle または Google Colab のノートブックで QLoRA/LoRA 学習を再現できる(無料枠の制限内で完走することを実測確認する)
- [ ] 学習済みLoRAをローカル(4GB)にダウンロードして、ベースモデル+アダプタ切替で推論できる
- [ ] 「LoRAなし」と「LoRAあり」を同じ評価セットで比較できる
- [ ] 複数ゲーム共通LoRA(干渉の有無の検証)は、各ゲーム個別LoRAと評価基準が揃った後にのみ実施する

**優先度**: P1(重要。いずれかのゲームの認識精度が目標に届かない場合にのみ着手。届けばKaggle / Colabは使わない)

## 非機能要件

実現方式は `03_ARCHITECTURE-DESIGN.md` が正本。ここでは満たすべき基準のみ定める。

### パフォーマンス
- 推論時のGPUメモリ使用量: **4GB以内**(ゲーム本体と同時に動作させた状態で)
- 1手あたりの所要時間: セカンダリーKPIの基準に従う。リアルタイム性は要求しない
- 古典的画像処理による盤面認識: 1画面あたり **1秒以内(仮)**
- 思考ロジック: GPUを使わず、1手あたり **10秒以内(仮)**

### ユーザビリティ
- 新しい画面に対する座標キャリブレーションを、手順書に従って **30分以内(仮)** に完了できる
- 失敗時は停止理由と対象画像が出力され、ログだけで原因調査を開始できる

### 信頼性
- 画面変化なし・同一状態の繰り返し・ステップ上限超過のいずれでも、無限ループせず停止する
- 緊急停止キー押下後 **1秒以内** に操作を止める(仮)
- 認識失敗時に推測で操作しない(信頼度が閾値未満なら停止)

### セキュリティ・コンプライアンス
- 外部へのデータ送信なし(推論はすべてローカル。クラウドGPUは学習データとLoRA学習のみで使用)
- 学習データにアカウント情報・個人情報を含めない(スクショ取得時にマスク/除外)
- シングルプレイ/CPU戦のみを対象とし、オンライン対戦での自動操作は行わない
- 強いクラウドVLMに軌跡を生成させてデータ化する場合は、事前に当該サービスの利用規約を確認する

### 保守性・拡張性
- ゲーム追加で共通基盤を変更しない(KPI参照)
- 認識手段(OpenCV / CNN / VLM)をモジュール単位で差し替えられる
- 対応OS: Windows 11(PC操作前提)。Python のバージョン等は `03` で定義

## 前提・制約・未確定事項

| 項目 | 内容 | 確認方法 |
|---|---|---|
| 大戦略SSB2のルール | `docs/ideas/大戦略SSB2_ルール.pdf`(テキスト抽出可)を開発時の入力とする。地形防御と拠点の数値は記載あり。兵器ごとの性能、移動力消費、ダメージ計算式は記載なし | 不足分はゲーム内画面から取得(Phase 0で確認) |
| 大戦略SSB2の勝敗 | 敵の首都をすべて占領すると勝利。自分の首都を占領されるか、最大99ターンを超えると敗北 | ルールブックで確認済み |

## スコープ外

明示的にスコープ外とする項目:
- リアルタイムアクションゲームの自動プレイ(VLM遅延が前提に合わない)
- オンライン対戦・ランキング等での自動操作(規約違反のおそれ)
- 任意のゲームに対応する汎用エージェント(大規模モデルの領域)
- ゲームごとの別モデルのフルファインチューニング
- 4GB環境でのVLMのローカル学習(VLMのLoRA学習はKaggle/Colab。認識用の小型CNNはローカルで学習してよい)
- 強化学習による本格的な自己対戦基盤(P2で検討)
- Android端末側でのモデル実行(推論はPC上で行う)
