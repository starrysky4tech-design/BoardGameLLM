ゲーム特化のローカルLLMを作るなら、「画面を見て行動を決めるVLM(画像対応LLM)」をベースにして、小型モデルをファインチューニングする構成が現実的です。

## 1. 推奨モデル

ゲームは画面(画像)が入力なので、テキストのみのLLMではなくVLMを選びます。

| 用途 | 候補 | 備考 |
|---|---|---|
| 本命ベース | **Qwen3-VL(2B/4B/8B/32B、MoE版30B-A3B)** | GUIエージェント向けの対話データを学習に加えたVLMで、サイズ展開が広くローカル向けです |
| GUI操作特化 | **UI-TARS 1.5 7B** | Qwen2.5-VL-7Bをベースにしたコンピュータ操作用のGUIエージェントで、ゲームでも評価されているので、クリック位置の精度が必要なゲーム向きです |
| 参考(論文) | Game-TARS | キーボード・マウスの入力に対応した汎用ゲームエージェントとして発表されています。ローカルで使えるかは別途確認が必要です |

目安は次のとおりです。
- **VRAM 8〜12GB**: Qwen3-VL-4B/8B(4bit量子化)
- **VRAM 16〜24GB**: Qwen3-VL-8B(軽めの量子化)、UI-TARS 7B、30B-A3B(量子化)
- ゲームをしながら推論するとVRAMを奪い合うので、**ゲームを軽め設定にするか、推論用にGPUを分ける**とよいです。

## 2. 開発手順

**Step 1: 環境を決める**
- 最初はPC版かAndroidエミュレータ(adbで操作できる)が扱いやすいです。
- 画面取得は PC: `mss`、Android: `adb exec-out screencap`、操作は PC: `pyautogui`/`pydirectinput`、Android: `adb shell input`。
- 推論サーバは **Ollama / llama.cpp / vLLM / LM Studio** のいずれか(OpenAI互換APIにすると差し替えやすい)。

**Step 2: 学習せずに動かす(プロンプトのみのエージェント)**
1. 画面をキャプチャして縮小(例: 720p前後)。
2. 「現在の画面・目的・直前の行動」をプロンプトに入れる。
3. モデルは `{"action":"tap","x":..,"y":..}` のようなJSONだけを返す。
4. 実行して次フレームへ、というループにします。

ここで **どこまで素のモデルでできるか** を測ります。ターン制や、メニュー操作中心のゲーム(ソシャゲの周回など)ならこれだけで動くこともあります。

**Step 3: 評価の仕組みを作る**
- 対象ゲームの「タスク」を10〜30個決める(例: ステージ1クリア、ガチャ画面まで移動)。
- 成功率、1タスクあたりのステップ数、誤操作率を毎回記録します。ここを省くとチューニングの効果が見えなくなります。

**Step 4: データ収集**
- 自分でプレイして、`(スクショ, 行動, 目的)` を自動ログします。数百〜数千件から効果が出ることもあります。
- 強いモデル(クラウドVLMなど)にプレイさせて成功した軌跡を集める方法もあります。その場合は利用規約を確認してください。
- 失敗した場面は「正解行動」を後から付け直すと効率よく学習データになります。

**Step 5: ファインチューニング**
- **QLoRA/LoRA** が基本です(フル学習は不要)。ツールは Unsloth、LLaMA-Factory、ms-swift など。
- 先行例として、Qwen2.5-VLとUI-TARSを組み合わせた戦略ゲーム自動化のYanyun-3は、複数ゲームのデータでQLoRAによるファインチューニングを行っています。小規模データでも効果が出る参考になります。
- 画像、行動、座標の形式を一貫させてください。座標は正規化するか、解像度を固定します。

**Step 6: 高速化と実運用**
- 量子化(GGUF Q4など)、入力画像の縮小、思考(推論)出力の短縮で遅延を減らします。
- リアルタイムアクションゲームはVLMの遅延(数百ミリ秒〜数秒)がボトルネックです。その場合は、**VLMが方針を決め、軽量な処理(OpenCV、小型CNN、ルールベース)が即時操作をする二層構成**にします。
- 無限ループや誤タップ対策に、ステップ上限、画面変化なしの検出、緊急停止キーを入れます。

**Step 7: 余力があれば強化学習**
- 成功/失敗を報酬にして改善する手法もあります。ただし環境を高速に何度も回す必要があり、難度が高いです。まずはStep 5までで十分です。

## 3. 注意点と現実的な見立て

- **ゲームの種類で難度が大きく変わります**: ターン制・UI中心は容易、リアルタイムアクションは難しいです。
- **規約**: オンラインゲームでの自動操作(bot)は、多くのタイトルで規約違反でBANの対象です。シングルプレイや、自分で用意した環境、研究目的に絞るのが安全です。
- 最初から「ゲーム特化LLMを一から作る」のではなく、**既存VLM+LoRA+自作ハーネス(画面取得と操作)**が最短です。

はい、ボードゲームで画面の動きが小さいなら、VRAM 4GBでも十分現実的です。ただし、LLMに何をやらせるかを絞る設計にするのがコツです。

## 結論

- **推論(実行)**: Qwen3-VL-2B、余裕を見ても4Bまでの4bit量子化が候補です。ボードゲームは1手に数秒かかっても問題ないので、遅いのは致命的ではありません。
- **学習(ファインチューニング)**: 2BのQLoRAを画像解像度を落として試す程度が限界です。本格的に学習するなら、Colabなどのクラウドで学習し、完成したモデルだけ手元で動かすのが無難です。
- 以下のサイズは目安です。実際はコンテキスト長や画像解像度でVRAM消費が変わるので、実測して調整してください。

## サイズの目安(4bit量子化時)

| モデル | 目安 | 4GBでの見通し |
|---|---|---|
| Qwen3-VL-2B | 重み約1.5GB+画像エンコーダ | 余裕あり |
| Qwen3-VL-4B | 重み約2.5GB+画像エンコーダ | ぎりぎり。画像を小さくし、コンテキストを短くすれば可能 |
| 8B以上 | 4GB超 | CPUオフロード前提になり、低速になる |

動かし方は **llama.cpp / Ollama / LM Studio** のGGUF版が簡単です。一部の層をCPU/RAMに逃がすこともでき、ボードゲームなら遅さを許容できます。

## ボードゲームなら、設計をこうすると有利です

LLMに「次の最善手」まで考えさせると、小型モデルでは弱くなります。役割を分けるのが定石です。

1. **盤面認識(VLM or 画像処理)**: スクショから盤面を読み取り、駒配置などの構造化データ(例: FEN、SGF、二次元配列)にします。
2. **思考(ゲームエンジン)**: 将棋、囲碁、チェスなど既存の専用エンジンや探索アルゴリズムに最善手を求めます。ゲームが独自ルールなら、ルールを自分で実装して探索(MCTS、αβ法など)させます。
3. **操作(自動化)**: 決まった手を、座標に変換してクリックまたはタップします。

こうすると、VLMに求める能力は盤面を正しく読むことだけになり、小型モデルでも十分です。

さらに、盤面がグリッド状で見た目が固定なら、**VLMを使わずOpenCVのテンプレートマッチングや小型CNNで認識する**方法もあります。こちらのほうが速く、VRAMもほとんど使いません。まずこれで試して、うまくいかなければVLMに切り替える順序が効率的です。

## 4GB環境での開発の進め方

1. まず盤面認識だけ試す(OpenCV → 駄目ならQwen3-VL-2Bにゼロショットで読ませる)。
2. 認識精度が足りなければ、盤面スクショと正解配置のペアを数百枚集めてLoRAで学習します。盤面は自動生成しやすいので、データ作りが楽です。
3. 探索エンジンと接続して、1手ずつ自動で打てるようにします。
4. 評価は「盤面認識の正答率」と「エンジン相手の勝率」の2つを別々に見ます。

どちらもターン制なので、4GB VRAMでも成立します。ただし、既存のボードゲームエンジンは使えません。**盤面認識、ルール実装、思考、操作を自作する**構成になります。なお「大戦略SSB2」の詳細なルールやUI仕様は私の手元に確かな情報がないため、以下は一般的な六角形(ヘクス)マップのターン制戦略ゲームを想定した設計です。実物を見て調整してください。

## 全体構成(両ゲーム共通)

```
画面取得 → 状態認識 → ゲーム状態(構造化データ) → 思考 → 操作変換 → 入力 → 画面変化の確認
```

- 共通化できるのは**画面取得、操作、ループ、ログ**の部分です。**認識とルール(思考)はゲームごとに別モジュール**にします。
- LLM/VLMは主に「認識の補助」と「想定外画面(ダイアログなど)の判断」に使い、**戦術の中身は自作ロジック**に任せるのが、小型モデル・4GBでは堅実です。

## 画面取得と操作

**PC(大戦略SSB2)**
- 取得: `mss` や `dxcam`(ウィンドウ指定。古いソフトはウィンドウモード+固定解像度にすると座標が安定します)
- 操作: `pyautogui` が効かない場合は `pydirectinput` や Win32 `SendInput`。古いゲームは管理者権限での実行が必要なことがあります。
- 解像度とウィンドウ位置を固定し、すべての座標をウィンドウ相対で扱います。

**Android(独自ルールのゲーム)**
- ミラーアプリ(scrcpyなど)の**ウィンドウをキャプチャする**方法もありますが、`adb exec-out screencap -p` で直接取得し、`adb shell input tap x y` で直接操作するほうが安定します。ミラー画面のクリックは位置ずれや遅延の原因になるので、ミラーは人間の確認用にとどめるのがお勧めです。
- ミラーアプリを使う場合はウィンドウ固定とDPI設定に注意してください。

## 状態認識

1. **グリッド座標を確定する**: ヘクスマップなら、基準点とヘクスのサイズから「画面座標⇔ヘクス座標」の変換式を作ります(最初に手でキャリブレーション)。スクロールやズームがあるなら、スクロール量の検出も必要です。
2. **各マスの中身を読む**: 地形、ユニット種別、所属(色)、HPなどを、画像処理でマスごとに切り出して分類します。
   - まず**OpenCVのテンプレートマッチング**で試します(ゲーム画面は見た目が一定なので、これで相当読めます)。
   - 難しい部分(数字、状態表示)は、**小型CNNの分類器**か**OCR**を使います。
   - それでも足りない箇所だけ、Qwen3-VL-2B等に切り出し画像を渡して読ませます。
3. **UI状態(メニューが開いている、確認ダイアログ等)を判定**して、状態に応じた処理に分岐させます。

大戦略系はユニット数が多く、認識の手間が最大の山です。**先に、ゲーム内に数値や一覧を表示できる画面(部隊一覧など)があるなら、それを読むほうが楽**なことがあります。

## 思考(ルール実装)

- ゲームのルール(移動力、地形コスト、攻撃・反撃、生産、占領など)を自分でコード化し、**盤面状態から合法手を列挙できる**シミュレータを作ります。公式のルールブックや実測データから数値を集めます。
- AIは最初は**単純な評価関数+貪欲法**から始めます。例:
  - 目標都市への最短経路で前進
  - 攻撃可能なら最も有利な交換比を選ぶ
  - 資金に応じて生産
- 慣れてきたら、数手先の探索(ビームサーチなど)に発展させます。
- 独自ルールのAndroidゲームは、**ルールが不明な部分を観察ログから学ぶ**必要があります。プレイを記録して、実際の挙動とシミュレータを突き合わせて直します。

## 開発手順(推奨順)

1. **ウィンドウ取得と操作の確認**: スクショを撮り、指定座標をクリックできるところまで(大戦略とAndroidそれぞれ)。
2. **座標キャリブレーションとマス認識**: 画面から盤面データを再現できるか、デバッグ画像(認識結果を重ね描き)で確認します。
3. **認識の正答率を測る**: 手でラベル付けした数十画面と比較します。
4. **ルールシミュレータ作成**: まず「1ターン分の合法手が出せる」ところまで。
5. **簡単なAIで1ターン自動操作**: 人が見守りつつ1手ずつ実行 → 数ターン → 1ゲーム。
6. **ログと失敗リプレイ**: 誤認識した画面を保存し、テンプレートや分類器を改善します。
7. (必要なら)LoRAでVLMを学習: 認識が手法1〜3で足りない場合にだけ。4GBの学習は厳しいので、クラウドで学習して手元で使うのが無難です。

## この規模のリスク

- **盤面が大きく、スクロールが必要**だと、認識の工数が一気に増えます。
- **古いPCソフト**は、キャプチャや入力が通らないことがあります(DirectDraw等)。早めに技術検証(手順1)を。
- **ルールの再現**に時間がかかります。最初は「正確なシミュレーション」ではなく、「人間の定石を真似るルールベース」でも動かせます。
- 規約やオンライン対戦での利用は避けてください。シングルプレイ・CPU戦限定が安全です。

[私の質問]
ちなみに、AndroidゲームのLLMを作る場合、ゲームごとにLLMを分ける or １つのLLMで複数ゲームに利用できるのどちらになる？

====================

結論から言うと、**ベースモデルは1つで共通にして、ゲームごとの差分(LoRAアダプタや設定)を切り替える**のが現実的です。ゲームごとにまったく別のLLMを作る必要はありませんが、完全に1つのまま全ゲームに対応させるのも、小型モデルでは難しいです。

## 3つの選択肢

**A. ゲームごとに別モデル(フルのファインチューニング)**
最も精度は出やすいですが、4GB環境ではストレージ・学習コスト・管理の面で非現実的です。おすすめしません。

**B. 共通ベースモデル+ゲームごとのLoRA(推奨)**
Qwen3-VL-2B/4Bなどを1つ置き、ゲームごとに小さなLoRAアダプタ(数十MB〜数百MB程度)を用意して切り替えます。VRAMにはベースモデル1つ分しか載らず、ゲーム切り替え時にアダプタだけ差し替えられます。llama.cppなどはLoRAの読み込みに対応しています。

**C. 1つのLoRAを複数ゲームのデータで学習**
ゲームの画面が似ている(同じ種類の盤面ゲームなど)なら、これも有効です。ただし、ゲーム同士で干渉して精度が落ちることがあり、2Bクラスでは特に起こりやすいです。ゲームIDをプロンプトに入れて区別させますが、効果は試して確かめる必要があります。

## 今回のケースでの見立て

前回の設計では、LLM/VLMの役割は「認識の補助」に絞っていました。この場合、**共通化の境界は次のようになります**。

- **共通にできる部分**: 画面取得、操作、ループ、ログ、ベースVLM、プロンプトの枠組み
- **ゲームごとに分ける部分**: ルール実装、思考ロジック、認識用のテンプレート・分類器、(必要なら)LoRA

つまり「LLMを分けるか」よりも、**ゲームごとのルールと認識はプラグインとして分け、共通基盤の上に載せる**設計が本質です。

```
共通基盤(取得・操作・ループ・VLM)
 ├─ 大戦略SSB2プラグイン(認識・ルール・AI)
 └─ 独自ルールゲームプラグイン(認識・ルール・AI)
```

これなら、3つ目のゲームを追加するときもプラグインを足すだけで済みます。

## 判断の目安

- 最初は**ベースモデル1つ、LoRAなし**で始め、認識が足りないゲームだけLoRAを作る。
- 複数ゲームで同じLoRAを試すのは、各ゲームで個別LoRAが作れて、評価基準もできた後にします。比較できる状態にしてからでないと、干渉の有無が判断できません。
- 「1つのLLMがどんなゲームでも遊べる」汎用エージェントは、大規模モデルの領域です。4GB・小型モデルで狙うなら、ゲームごとのプラグイン方式のほうが確実に動きます。
